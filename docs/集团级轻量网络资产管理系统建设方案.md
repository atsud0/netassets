# 集团级轻量网络资产管理系统建设方案

> 文档状态：方案基线稿  
> 版本：V0.1  
> 更新日期：2026-07-15  
> 适用范围：集团及下属子公司网络资产统一填报、管理、审核与统计

---

## 1. 文档说明

本文档用于明确集团级轻量网络资产管理系统的产品定位、组织与权限模型、核心业务流程、功能范围、数据结构、插件边界、技术架构及版本计划，可作为后续需求评审、原型设计、数据库设计和开发实施的基线。

本方案已确认以下基本前提：

1. 系统服务于集团及其下属子公司，不是单一公司或个人使用的资产台账。
2. 集团负责制定资产标准、下发填报任务、审核数据、查看全局统计。
3. 子公司负责登记业务系统、录入网络资产并持续维护。
4. 系统保持轻量，不建设完整 CMDB、漏洞管理或安全运营平台。
5. 自动发现、DNS 探测、HTTP 检测等能力不进入核心系统，后续以插件形式加入。
6. 系统优先支持集团内部私有化部署。

## 2. 产品定位

### 2.1 产品定义

本系统是一个面向集团和多级子公司的轻量网络资产管理与填报平台。

集团通过系统统一管理组织机构、业务系统和网络资产，并向子公司下发周期性或专项资产填报任务；子公司在自身数据权限范围内登记业务系统、录入或导入网络资产、修正数据问题并提交集团审核，最终形成可查询、可追溯、可导出的集团网络资产台账。

### 2.2 核心对象

系统围绕以下四类核心对象建设：

```text
集团/子公司（组织机构）
  └─ 业务系统
      └─ 网络资产
          ├─ 域名
          ├─ IP 地址
          ├─ URL/网站
          ├─ 网络服务
          └─ 其他网络资产

集团
  └─ 资产填报任务
      └─ 子公司填报、提交、审核、退回和归档
```

### 2.3 核心价值

- 统一集团网络资产的数据标准。
- 明确资产归属公司、关联系统和责任人。
- 支持子公司自主填报和日常维护。
- 支持集团集中审核、统计和导出。
- 识别集团范围内的重复、冲突和无归属资产。
- 保留完整的资产变更记录和用户操作日志。
- 通过插件扩展自动发现等非核心能力。

### 2.4 建设原则

1. **轻量优先**：不建设与资产台账无关的复杂平台能力。
2. **集团统筹**：标准、任务、审核和全局统计由集团统一管理。
3. **属地维护**：子公司负责自身系统与资产数据的准确性。
4. **权限隔离**：子公司默认只能访问自身及授权范围内的数据。
5. **全程留痕**：新增、修改、删除、审核、导入和导出均可追溯。
6. **核心稳定**：不安装插件时，核心系统仍可独立完整运行。
7. **插件扩展**：自动发现、检测、通知和外部同步通过插件提供。
8. **数据可进可出**：重点保障 CSV/XLSX 导入、校验和导出体验。

## 3. 建设目标与非目标

### 3.1 第一阶段建设目标

第一阶段应实现以下完整业务闭环：

```text
集团创建子公司和账号
  ↓
集团下发资产填报任务
  ↓
子公司登记业务系统
  ↓
子公司在线录入或批量导入网络资产
  ↓
系统执行格式、完整性和重复校验
  ↓
子公司提交填报结果
  ↓
集团审核或退回
  ↓
审核通过并形成集团资产台账
  ↓
集团统一查询、统计和导出
```

### 3.2 第一阶段不建设的内容

- 漏洞扫描和漏洞生命周期管理。
- 大规模公网资产测绘。
- 服务器性能和网络流量监控。
- Agent 客户端。
- 复杂资产依赖拓扑。
- 工单系统和复杂审批流。
- 自动修复和安全处置。
- 完整云资源管理平台。
- 多租户 SaaS 商业化能力。
- 字段级动态权限体系。
- 任意第三方代码在线上传和执行。

## 4. 组织机构模型

### 4.1 组织层级

系统支持集团、子公司和部门的树形结构，例如：

```text
XX集团
├── A科技有限公司
│   ├── 信息技术部
│   └── 电商事业部
├── B金融服务有限公司
├── C信息技术有限公司
└── D海外业务有限公司
```

业务系统和网络资产的主要归属单位应为集团或子公司等公司级组织；部门用于记录维护或责任归属，不作为集团统计时的主要法人归属。

### 4.2 组织字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| 组织名称 | 是 | 集团、公司或部门完整名称 |
| 组织简称 | 否 | 列表和报表中的显示名称 |
| 组织编码 | 是 | 集团范围内唯一 |
| 组织类型 | 是 | 集团、子公司、部门、其他 |
| 上级组织 | 否 | 集团根节点无上级组织 |
| 组织负责人 | 否 | 组织管理负责人 |
| 联系人 | 否 | 资产填报联系人 |
| 联系方式 | 否 | 邮箱或电话 |
| 状态 | 是 | 启用、停用 |
| 备注 | 否 | 补充说明 |

### 4.3 组织管理规则

- 组织编码在集团范围内唯一。
- 停用组织后，历史资产数据继续保留。
- 存在下级组织时不能直接删除上级组织。
- 存在业务系统或资产归属关系时，默认不允许永久删除组织。
- 组织调整必须写入操作日志。

## 5. 用户、角色与数据权限

### 5.1 集团角色

#### 集团超级管理员

- 管理组织机构、用户、角色和系统设置。
- 查看和修改全集团业务系统及资产。
- 管理插件、备份和恢复。
- 查看全部审计日志。

#### 集团资产管理员

- 查看全集团业务系统和网络资产。
- 创建和管理资产填报任务。
- 审核、退回子公司提交的数据。
- 处理重复资产和归属冲突。
- 查看集团统计并导出集团台账。

#### 集团审核员

- 查看全集团填报数据。
- 审核或退回子公司提交内容。
- 查看数据变更和数据质量问题。
- 默认不能直接替子公司修改原始数据。

#### 集团查看者

- 查看全集团资产和统计数据。
- 根据授权导出数据。
- 不能新增、修改、删除或审核。

### 5.2 子公司角色

#### 子公司管理员

- 管理本公司用户。
- 登记和维护本公司业务系统。
- 管理本公司网络资产。
- 执行批量导入和导出。
- 提交集团填报任务。
- 查看本公司操作记录和退回意见。

#### 子公司资产编辑者

- 新增、编辑本公司业务系统和网络资产。
- 使用 CSV/XLSX 批量导入。
- 处理集团退回的数据问题。
- 不能管理用户和组织机构。

#### 子公司查看者

- 查看和导出本公司数据。
- 不能新增、编辑、删除和提交审核。

### 5.3 数据范围

系统内置以下数据范围：

```text
全集团
本组织及下级组织
本组织
本人负责的数据
```

每个用户的最终权限由“功能权限”和“数据范围”共同决定。

### 5.4 多组织任职

一个用户可以被授权管理多个组织，例如：

```text
用户王某
├── A公司：查看者
├── B公司：资产管理员
└── C公司：审核员
```

用户可以切换当前组织视角，集团级角色可以直接查看全集团数据。

### 5.5 权限实现原则

- 所有数据权限必须由后端接口强制校验。
- 不能仅通过前端隐藏菜单实现权限隔离。
- 导入、导出、插件任务和候选资产同样必须进行组织权限校验。
- 子公司上传文件时，不能通过篡改文件内容向其他公司写入数据。
- 集团审核员默认只审核、不代替子公司直接修改原始数据。

## 6. 业务系统管理

### 6.1 业务系统定位

业务系统是一等核心对象，用于承接组织和网络资产之间的业务关系。

```text
所属公司
  ↓
业务系统
  ↓
域名、IP、URL和网络服务
```

### 6.2 业务系统字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| 系统名称 | 是 | 例如客户服务平台 |
| 系统编码 | 是 | 集团范围内唯一或按集团规则生成 |
| 所属公司 | 是 | 系统主要归属公司 |
| 所属部门 | 否 | 具体维护部门 |
| 系统简称 | 否 | 列表显示名称 |
| 系统负责人 | 是 | 业务或技术负责人 |
| 联系方式 | 否 | 邮箱、电话等 |
| 系统状态 | 是 | 建设中、运行中、暂停使用、已下线、已归档 |
| 系统等级 | 是 | 一般、重要、核心 |
| 部署方式 | 否 | 自建机房、云平台、混合部署等 |
| 互联网暴露情况 | 是 | 是、否、部分、未知 |
| 建设厂商 | 否 | 自研或第三方厂商 |
| 系统描述 | 否 | 业务用途和范围 |
| 上线时间 | 否 | 正式上线时间 |
| 下线时间 | 否 | 计划或实际下线时间 |
| 创建人/时间 | 是 | 系统自动记录 |
| 更新人/时间 | 是 | 系统自动记录 |

### 6.3 系统状态

```text
建设中
运行中
暂停使用
已下线
已归档
```

### 6.4 系统管理功能

- 新增、编辑、查看和软删除业务系统。
- 按公司、部门、负责人、状态、等级和互联网暴露情况筛选。
- 批量修改负责人、状态、等级和所属部门。
- 关联或解除网络资产。
- 查看系统变更历史。
- 查看系统在填报任务中的审核状态。
- 查看系统关联的域名、IP、URL和网络服务。

### 6.5 业务系统数据安全属性

业务系统除基本信息和网络资产外，还应支持扩展数据安全属性。这类属性归属于业务系统，不直接归属于域名、IP 等单条网络资产；网络资产可以通过所关联的业务系统继承相应的风险和关注属性。

建议在业务系统详情页增加“数据安全”页签，记录以下信息：

| 字段 | 类型 | 建议选项或说明 |
|---|---|---|
| 是否处理个人信息 | 枚举 | 是、否、未知 |
| 是否处理敏感个人信息 | 枚举 | 是、否、未知 |
| 个人信息类型 | 多选 | 身份信息、联系方式、金融账户、行踪轨迹、生物识别、医疗健康、未成年人信息、其他 |
| 是否包含未成年人信息 | 枚举 | 是、否、未知 |
| 涉及自然人数 | 数字 | 受数据处理活动影响或涉及的自然人数 |
| 个人信息记录量 | 数字 | 系统存储或处理的个人信息记录条数 |
| 数据量区间 | 枚举 | 1万以下、1万至10万、10万至100万、100万至1000万、1000万以上、未知 |
| 是否超过10万条 | 派生字段 | 由个人信息记录量或数据量区间自动计算，不允许手工维护 |
| 数据统计口径 | 文本 | 例如有效用户数、客户主表记录数、交易明细记录数 |
| 数据基准日期 | 日期 | 本次数据量统计对应的日期 |
| 是否为估算值 | 布尔 | 标记数据量是否为估算结果 |
| 是否涉及重要数据 | 枚举 | 是、否、待识别 |
| 是否涉及核心数据 | 枚举 | 是、否、待识别 |
| 数据敏感等级 | 枚举 | 按集团数据分类分级标准配置 |
| 是否包含商业秘密 | 枚举 | 是、否、未知 |
| 是否包含客户数据 | 枚举 | 是、否、未知 |
| 是否包含员工数据 | 枚举 | 是、否、未知 |
| 是否向第三方提供 | 枚举 | 是、否、未知 |
| 是否存在跨境传输 | 枚举 | 是、否、未知 |
| 数据存储位置 | 文本或选项 | 自建机房、云平台、境内区域、境外区域等 |
| 数据保留期限 | 文本或数字 | 按集团统一口径填写 |
| 分类分级状态 | 枚举 | 已完成、进行中、未开展 |
| 填报人 | 用户 | 本次数据安全信息的填报人员 |
| 确认人 | 用户 | 对数据安全信息进行确认的人员 |
| 最近确认时间 | 日期时间 | 最近一次确认日期 |
| 补充说明 | 多行文本 | 统计口径、特殊情况和佐证说明 |

“涉及自然人数”“个人信息记录量”和“数据存储容量”是不同指标，不应混用。系统应优先保存原始数值、统计口径和基准日期，再根据集团规则自动计算“是否超过10万条”等关注标识，避免阈值调整后要求所有子公司重新填报。

### 6.6 固定字段与集团自定义字段

数据安全字段采用“核心固定字段 + 集团自定义字段”的组合方式：

- 集团经常统计、筛选和用于规则判断的字段采用固定字段。
- 专项检查或阶段性需求使用集团自定义字段。
- 自定义字段由集团管理员统一创建、命名和维护选项。
- 子公司只能填写被授权字段，不能自行创建同义字段破坏集团统计口径。
- 集团可以设置字段适用的组织、业务系统类型、填报任务、是否必填及填写说明。

自定义字段类型至少支持：

```text
单行文本
多行文本
数字
日期
单选
多选
是/否/未知
用户
组织
附件
```

例如年度数据安全盘点可以临时要求填写：

- 是否完成个人信息保护影响评估。
- 数据库加密方式。
- 数据脱敏方式。
- 第三方共享协议编号。
- 数据销毁周期。

### 6.7 数据安全关注规则

集团可以基于业务系统和网络资产的组合条件定义数据质量或高关注规则，例如：

```text
互联网暴露 = 是
且
涉及敏感个人信息 = 是
且
个人信息记录量 > 100000
```

系统可以据此形成以下视图：

- 公网暴露且涉及敏感个人信息的系统。
- 公网暴露且个人信息记录量超过10万条的系统。
- 涉及个人信息但长期未确认的系统。
- 涉及重要数据但尚未完成分类分级的系统。
- 存在跨境传输的系统。
- 已下线但仍保存个人信息的系统。

该能力用于集团数据治理、筛选和关注标记，不替代正式的合规认定或风险评估。

## 7. 网络资产管理

### 7.1 第一版支持的资产类型

- 域名。
- IP 地址，包括 IPv4 和 IPv6。
- URL/网站。
- 网络服务，例如 `192.168.1.10:443`。
- 其他网络资产。

### 7.2 网络资产字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| 资产类型 | 是 | 域名、IP、URL、服务、其他 |
| 资产值 | 是 | 资产主要标识 |
| 标准化值 | 是 | 系统用于去重和搜索 |
| 资产名称 | 否 | 便于用户识别 |
| 主归属公司 | 是 | 资产的主要责任公司 |
| 关联业务系统 | 否 | 可以关联一个或多个系统 |
| 维护部门 | 否 | 实际维护部门 |
| 负责人 | 否 | 资产责任人 |
| 环境 | 是 | 生产、预发布、测试、开发、办公、其他 |
| 网络位置 | 是 | 公网、内网、未知 |
| 资产状态 | 是 | 正常、待确认、停用、已归档 |
| 重要程度 | 是 | 一般、重要、核心 |
| 来源 | 是 | 手工、导入、API、插件 |
| 标签 | 否 | 多个标签 |
| 备注 | 否 | 补充说明 |
| 首次发现时间 | 否 | 插件发现时使用 |
| 最后发现时间 | 否 | 插件发现时使用 |
| 创建人/时间 | 是 | 系统自动记录 |
| 更新人/时间 | 是 | 系统自动记录 |

### 7.3 未归属系统资产

资产必须存在主归属公司，但可以暂时不关联业务系统。

常见场景包括：

- 文件导入后尚未完成系统归属梳理。
- 只知道资产属于某公司，不知道具体业务用途。
- 自动发现插件发现了新资产。
- 历史资产暂时无人认领。

系统应提供“未归属系统资产”视图，并在集团和子公司仪表盘中重点统计。

### 7.4 资产状态与审核状态分离

业务运行状态和数据审核状态不得混为一谈。

资产运行状态：

```text
正常
停用
已归档
待确认
```

数据审核状态：

```text
草稿
待审核
已通过
已退回
```

例如，一个运行状态为“正常”的资产，可以因为季度填报尚未审核而处于“待审核”状态。

## 8. 资产标准化、去重与归属冲突

### 8.1 标准化规则

#### 域名

- 去除首尾空格。
- 转换为小写。
- 去除末尾的点号。
- 国际化域名使用统一编码格式。

示例：

```text
API.Example.COM.
```

标准化为：

```text
api.example.com
```

#### IP 地址

- 校验 IPv4/IPv6 格式。
- IPv6 转换为统一表示形式。
- 去除多余空格。

#### URL

- 协议和主机转为小写。
- 去除默认端口。
- 统一根路径。
- 保留非默认端口、路径和查询参数。

#### 网络服务

统一标准化为：

```text
协议://主机:端口
```

例如：

```text
tcp://192.168.1.10:22
https://api.example.com:443
```

### 8.2 集团级唯一资产实体

同一个网络资产可能被多家子公司使用，但集团资产库不应简单生成多条重复实体。

推荐模型：

```text
资产实体
├── 主归属公司
├── 使用公司
├── 运维公司
├── 关联业务系统A
└── 关联业务系统B
```

资产实体在集团范围内按“资产类型 + 标准化值”进行重复检测。

### 8.3 重复录入处理

子公司录入已存在资产时，系统提示：

```text
该资产疑似已在集团资产库中存在。
```

子公司可以：

- 申请关联已有资产。
- 提交归属确认。
- 返回修改。
- 说明不是同一资产并提交集团审核。

集团管理员可以：

- 合并资产。
- 设置主归属公司。
- 将其他公司设置为使用或运维单位。
- 确认两条记录不是同一资产。
- 退回子公司补充说明。

### 8.4 隐私和权限处理

当重复资产属于其他子公司且当前用户没有查看权限时，只提示“集团内存在疑似重复资产”，不直接展示其他公司的敏感明细。

## 10. 资产填报任务

### 10.1 功能定位

集团通过填报任务组织季度盘点、年度盘点、安全专项检查或其他集中数据采集工作。

### 10.2 集团创建任务

任务配置包括：

- 任务名称。
- 任务说明。
- 参与子公司。
- 开始时间和截止时间。
- 需要填报的资产类型。
- 必填字段。
- 数据质量规则。
- 是否需要集团审核。
- 是否允许截止后提交。

### 10.3 状态设计

集团任务状态：

```text
草稿
进行中
已截止
已完成
已归档
```

子公司提交状态：

```text
未开始
填报中
已提交
已退回
已通过
逾期未提交
```

### 10.4 子公司填报流程

```text
打开填报任务
  ↓
确认现有业务系统和资产
  ↓
新增、编辑或批量导入数据
  ↓
执行完整性和重复校验
  ↓
修正数据问题
  ↓
提交集团审核
```

### 10.5 提交前检查

- 是否存在缺少负责人的核心系统。
- 是否存在缺少负责人的重要资产。
- 是否存在格式错误。
- 是否存在尚未处理的重复资产。
- 是否存在未关联业务系统的公网资产。
- 任务要求的必填字段是否完整。
- 是否存在待处理的集团退回意见。

### 10.6 集团审核

集团审核人员可以：

- 整体通过。
- 整体退回。
- 针对某个业务系统提出问题。
- 针对某条资产提出问题。
- 填写退回原因。
- 查看子公司修改前后的差异。
- 对整改后的内容再次审核。

### 10.7 日常维护与集中填报分离

为保持系统轻量，子公司日常维护不要求每次修改都经过集团审批。

- 日常修改：直接生效，但完整记录变更历史。
- 集中填报：按任务提交并由集团审核。
- 关键字段修改：可以进入专项审核。

建议纳入关键字段审核的内容：

- 主归属公司变更。
- 业务系统归属公司变更。
- 核心系统下线。
- 资产永久删除。
- 公网资产改为内网资产。
- 核心等级降低。
- 资产唯一标识修改。

### 10.8 任务快照

填报任务审核通过后生成数据快照，用于保留某一时间点的集团资产情况。

后续版本可以基于快照比较：

- 新增和下线的业务系统。
- 新增和消失的公网资产。
- 资产归属变化。
- 各公司资产数量变化。

## 17. 插件架构

### 17.1 插件定位

以下功能不进入核心系统，后续通过插件实现：

- 子域名发现。
- DNS 信息采集。
- HTTP/HTTPS 基础检测。
- SSL 证书检查。
- 端口检测。
- 消息通知。
- 云平台或第三方系统同步。

### 17.2 插件设计原则

1. 核心系统不依赖任何具体插件。
2. 插件通过核心服务接口操作正式资产，不直接随意修改核心表。
3. 插件维护自己的任务和原始结果表。
4. 插件发现结果先进入待确认资产，不直接进入正式台账。
5. 插件任务和结果必须带组织归属。
6. 子公司插件操作不能越过自身组织权限。
7. 第一阶段只支持官方内置模块化插件，不支持上传任意 ZIP 执行代码。

### 17.3 自动发现插件流程

```text
配置根域名和归属公司
  ↓
手动或定时执行发现任务
  ↓
发现子域名、DNS和基础HTTP信息
  ↓
执行集团范围重复检查
  ↓
写入对应公司的待确认资产
  ↓
子公司确认业务系统和负责人
  ↓
存在冲突时提交集团处理
  ↓
确认后录入正式资产台账
```

### 17.4 发现目标字段

- 根域名。
- 归属公司。
- 默认关联业务系统。
- 默认负责人。
- 授权说明。
- 执行周期。
- 超时时间。
- 最大并发数。
- 是否执行 DNS 解析。
- 是否执行 HTTP/HTTPS 检测。
- 是否启用。

### 17.5 核心插件接口

## 19. 技术落地方案

### 19.1 技术选型结论

系统第一版采用以下技术路线：

> Vue 3 + TypeScript 前端，Go 模块化单体后端，PostgreSQL 数据库，Podman Compose 私有化部署。

系统不采用微服务，不强依赖 Redis、消息队列、Elasticsearch 或 Kubernetes，优先保证集团内部部署简单、资源占用可控、后续维护方便。

### 19.2 总体技术架构

```text
浏览器
  │
  ▼
Vue 3 管理端
  │ REST/JSON API
  ▼
Go + Gin 后端
  ├─ 登录认证
  ├─ 组织权限
  ├─ 业务系统
  ├─ 网络资产
  ├─ 填报审核
  ├─ 导入导出
  ├─ 数据安全属性
  ├─ 审计日志
  ├─ 后台任务
  └─ 插件运行框架
  │
  ▼
PostgreSQL
  │
  ├─ 本地文件存储
  └─ S3兼容对象存储（可选）
```

第一版采用模块化单体架构：各业务模块在代码和数据库层保持明确边界，但统一构建、统一部署和统一运维。未来只有在任务量或部署规模确有需要时，才拆分独立 Worker 或其他服务。

### 19.3 前端技术栈

```text
Vue 3
TypeScript
Vite
Element Plus
Vue Router
Pinia
Axios
```

各组件职责：

| 技术 | 用途 |
|---|---|
| Vue 3 | 前端视图和组件框架 |
| TypeScript | 类型约束和前端可维护性 |
| Vite | 开发服务器和生产构建 |
| Element Plus | 表格、表单、组织树、对话框、文件上传等后台组件 |
| Vue Router | 页面路由和路由权限控制 |
| Pinia | 登录用户、当前组织、权限和公共配置等全局状态 |
| Axios | REST API 请求封装 |

Pinia 只保存真正的全局状态，例如：

- 当前登录用户。
- 当前组织视角。
- 当前用户权限。
- 公共字典和系统配置。

业务系统、资产和填报任务列表等服务端数据按页面请求，不将全部业务数据长期保存在全局状态中。

### 19.4 后端技术栈

```text
Go
Gin
pgx
sqlc
REST API
OpenAPI
```

各组件职责：

| 技术 | 用途 |
|---|---|
| Go | 后端业务、后台任务和插件运行框架 |
| Gin | HTTP 路由、中间件、参数绑定、校验和文件上传 |
| pgx | PostgreSQL 驱动和连接池 |
| sqlc | 根据显式 SQL 生成类型安全的 Go 数据访问代码 |
| REST API | 前后端通信和后续外部集成 |
| OpenAPI | 接口定义、文档和客户端类型生成 |

核心资产、组织权限、填报审核等查询优先采用显式 SQL，不依赖复杂 ORM 自动关联。这样可以清晰控制：

- 组织及下级组织查询。
- 多组织用户授权。
- 集团范围重复资产检查。
- 资产多组织归属关系。
- 业务系统与资产多对多关系。
- 填报任务审核状态。
- 数据安全属性组合筛选。
- SQL 索引和执行计划。

### 19.5 数据库技术方案

数据库使用 PostgreSQL。

主要使用的数据能力包括：

- UUID：业务实体主键。
- `inet`：单个 IPv4/IPv6 地址。
- `cidr`：IP 网段。
- `jsonb`：少量扩展数据和插件配置。
- 标准时间类型：创建、更新、审核和快照时间。
- 事务：资产导入、审核、合并和归属调整。
- 索引：组织、系统编码、标准化资产值和常用筛选字段。

字段设计原则：

- 经常查询、筛选、统计和规则判断的字段使用普通数据库列。
- 不常查询且不同类型差异明显的扩展信息可以使用 `jsonb`。
- 不把核心业务字段全部放入 JSON，避免后续统计和索引困难。
- 数据库变更全部使用版本化迁移脚本管理。

数据库迁移工具采用 Goose 或同类 Go 迁移工具，迁移文件随代码版本提交并在部署过程中按顺序执行。

### 19.6 登录认证

第一版使用：

```text
用户名和密码
+
服务端会话
+
HttpOnly安全Cookie
```

会话信息保存在 PostgreSQL，不强依赖 Redis。

该方案需要支持：

- 管理员停用用户后及时终止其访问。
- 修改角色后刷新权限。
- 强制指定账号退出。
- 查看和撤销当前登录会话。
- 会话过期。
- 登录失败次数限制。

认证模块预留适配接口，后续可以接入：

```text
OIDC
OAuth 2.0
LDAP/AD
集团统一身份认证
```

业务模块只依赖统一的当前用户和权限上下文，不直接依赖具体登录方式。

### 19.7 权限实现

权限由“功能权限”和“数据范围”共同决定。

功能权限示例：


数据范围：


后端通过统一的数据范围服务计算查询条件。组织权限不能分散在各个控制器中临时拼接，避免出现接口漏加组织过滤条件。

所有读取、写入、导入、导出、审核、后台任务和插件操作均必须使用同一套权限上下文。

### 19.8 后台任务

第一版不引入 Redis、RabbitMQ 或 Kafka，采用：

```text
PostgreSQL任务表
+
Go应用内Worker
```

后台任务包括：

- CSV/XLSX 导入。
- 大批量导出。
- 填报快照生成。
- 数据质量规则检查。
- 临时文件清理。
- 数据备份。
- 后续插件发现任务。

任务状态：

```text
pending
running
success
failed
cancelled
```

任务至少记录：

- 任务类型。
- 所属组织。
- 创建人。
- 任务参数。
- 当前进度。
- 成功、失败和跳过数量。
- 错误信息。
- 开始和完成时间。
- 重试次数。

第一版 Worker 可以与 Web API 运行在同一应用进程中，同时保留单独的 `worker` 启动入口；任务量增长后可以直接将 Worker 独立部署。

### 19.9 CSV/XLSX 处理

```text
CSV：Go标准库 encoding/csv
XLSX：Excelize
```

导入采用以下流程：

```text
上传文件
  ↓
保存临时文件
  ↓
创建导入任务
  ↓
后台解析
  ↓
写入临时数据或导入批次
  ↓
格式、权限、完整性和重复校验
  ↓

  ↓
事务批量写入正式表
  ↓
生成成功和失败报告
```

禁止在上传请求中直接逐行写入正式资产表，避免大文件阻塞请求，也便于提供预览、错误修正和重复处理。

### 19.10 文件存储

后端定义统一文件存储接口，业务代码不直接依赖本地路径或某个云厂商 SDK。

```go
type Storage interface {
    Put(ctx context.Context, key string, reader io.Reader) error
    Open(ctx context.Context, key string) (io.ReadCloser, error)
    Delete(ctx context.Context, key string) error
}
```

第一版提供两种实现：

1. 本地持久化目录，适用于简单单机部署。
2. S3 兼容对象存储，适用于集团已有 MinIO、私有云或其他对象存储环境。

建议目录分类：

```text
/data/uploads
/data/exports
/data/backups
```

导入、导出和备份文件应设置权限、保留期限和定期清理策略。

## 20. 非功能要求

### 20.1 性能目标

- 支持至少 10 万条网络资产的日常管理。
- 普通列表查询目标响应时间不超过约 1 秒。
- 万级数据导入不得阻塞普通 Web 请求。
- 大型导入和导出必须采用后台任务。
- 组织、系统编码、资产标准化值和常用筛选字段建立索引。

### 20.2 安全要求

- 密码使用安全哈希算法保存。
- 登录失败次数限制。
- 所有后端接口执行身份和数据范围校验。
- 文件类型、大小和内容校验。
- 防止 CSV/XLSX 公式注入。
- 导入文件隔离存储。
- 敏感配置加密保存。
- 重要操作完整审计。
- 插件不能绕过核心服务层修改正式资产。
- 默认按集团内部私有网络部署，不直接暴露公网。

### 20.3 备份恢复

- 管理员可以手动创建备份。
- 支持下载备份文件。
- 支持从备份恢复。
- 展示备份时间、大小和状态。
- 恢复操作需要二次确认。
- 定时备份可在后续版本增加。

### 20.4 可维护性

- 核心模块和插件模块明确分离。
- 数据库变更使用版本化迁移。
- 配置通过环境变量或配置文件管理。
- 所有后台任务可查看状态、进度和错误信息。
- 应用日志、任务日志和业务审计日志分开管理。

## 23. V1.0 验收标准

1. 集团管理员可以创建组织树、子公司和用户。
2. 用户只能访问自身角色和组织数据范围内的数据。
3. 子公司可以登记业务系统并维护负责人、状态和等级。
4. 子公司可以在线新增、编辑和软删除网络资产。
5. 网络资产可以关联一个或多个业务系统。
6. 同一资产被多家公司录入时，系统能够识别重复并进入关联或冲突处理流程。
7. 子公司可以通过 CSV/XLSX 导入业务系统和网络资产。
8. 错误数据不会导致整个导入任务失败。
9. 用户可以下载失败数据和具体原因。
10. 集团可以创建填报任务并选择参与子公司。
11. 子公司可以提交填报结果并接收集团退回意见。
12. 集团审核员可以通过或退回子公司提交的数据。
13. 集团可以查看各子公司的填报进度和数据质量情况。
14. 集团和子公司可以在授权范围内搜索、筛选和导出资产。
15. 业务系统和资产修改均有变更记录。
16. 登录、导入、导出、审核和删除等重要操作均有审计日志。
17. 删除的数据可以从回收站恢复。
18. 系统可以通过 Podman Compose 完成私有化部署。
19. 系统数据可以备份并成功恢复。
20. 未安装任何插件时，核心系统仍然完整可用。

## 24. 已确定的产品决策

| 决策项 | 当前结论 |
|---|---|
| 产品定位 | 集团级轻量网络资产管理与填报平台 |
| 使用主体 | 集团及下属多级子公司 |
| 核心层级 | 组织机构 → 业务系统 → 网络资产 |
| 部署形态 | 集团内部私有化部署 |
| 多租户 SaaS | 第一版不做 |
| 组织能力 | 支持集团、子公司和部门树 |
| 数据权限 | 全集团、本组织及下级、本组织、本人负责 |
| 业务系统 | 一等核心对象 |
| 数据安全属性 | 归属于业务系统，支持个人信息、敏感个人信息、数据量、分类分级等字段 |
| 数据量阈值 | 保存原始数值、统计口径和基准日期，是否超过10万条等由规则自动计算 |
| 自定义字段 | 由集团统一定义和维护，子公司按权限填写 |
| 网络资产模型 | 集团统一资产实体 + 多组织关系 + 多系统关联 |
| 日常修改 | 直接生效并记录变更 |
| 集中盘点 | 通过填报任务提交、审核和退回 |
| 删除方式 | 默认软删除 |
| 导入格式 | CSV、XLSX |
| 自动发现 | 不进入核心，后续通过插件加入 |
| 插件结果 | 先进入待确认资产，不直接进入正式台账 |
| 插件方式 | 官方内置模块化插件优先 |
| 第三方插件上传 | 第一版不支持 |
| 后端架构 | 模块化单体 |
| 前端建议 | Vue 3 + TypeScript + Element Plus |
| 后端建议 | Go + REST API |
| 数据库 | PostgreSQL |
| 大型任务 | PostgreSQL任务表 + 应用内Worker |
| 部署方式 | Podman Compose 优先 |

## 26. 总结

本系统的准确定位为：

> 一个面向集团和多级子公司的轻量网络资产管理与填报平台。集团负责标准、任务、审核和全局统计，子公司负责业务系统登记、网络资产录入和持续维护，自动发现及其他检测能力通过插件扩展。

核心业务关系：

```text
组织机构
  ↓
业务系统
  ↓
网络资产
```

核心管理闭环：

```text
集团下发任务
  ↓
子公司填报
  ↓
系统校验
  ↓
集团审核
  ↓
形成集团统一台账
```

核心架构原则：

```text
统一资产实体
+ 多组织归属
+ 多业务系统关联
+ 后端数据范围权限
+ 填报审核闭环
+ 完整变更留痕
+ 插件化扩展
```
