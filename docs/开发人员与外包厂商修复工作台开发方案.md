# 开发人员与外包厂商修复工作台开发方案

> 文档状态：第一期差异项已补齐；最新实现、验收与部署记录见第 18 节
> 版本：V1.3
> 更新日期：2026-10-03
> 适用项目：NetAssets
> 代码基线：`ff955f2`，数据库迁移截至 `00050_security_test_requests.sql`
> 已确认业务决策：组织管理员直接派单给具体人员；集团安全人员负责最终复测。

## 1. 目标与实施范围

在现有组织级安全整改工单之下增加分配到个人的修复任务，为内部开发人员、运维人员及外包厂商人员提供独立的修复工作台。

组织继续承担整改责任，执行人员负责修复和提交证据，集团安全人员负责技术复测和最终处置。第一期采用统一身份认证、独立工作台、任务级数据授权。

### 1.1 已确认决策

1. 组织管理员直接选择具体人员派单。
2. 内部开发和外包人员使用同一修复工作台。
3. 厂商按公司建档，操作落实到个人账号。
4. 派给外部人员不改变漏洞及主工单的责任组织。
5. 执行人员只能处理明确分配给自己的任务。
6. 集团安全人员负责最终复测；提交修复不会自动关闭漏洞。

### 1.2 本文采用的第一期设计默认值

以下规则用于形成可开发的完整方案，属于设计默认值，不代表用户逐项确认：

- 一项修复任务对应一个主工单中的一个漏洞，只有一个当前负责人。
- 支持批量派单；第一期不增加协作人或厂商负责人二次分派。
- 执行人员提交后，先经组织管理员确认，再交集团复测。
- 外部人员合作授权限定到责任组织、具体业务系统及有效期。
- 第一期开通方式采用管理员创建或一次性邀请，不提供公开自主注册。
- 先使用站内消息；邮件、企业消息、SSO 和 MFA 集成为后续扩展，不作为已有能力描述。
- 未关联业务系统的漏洞需先补齐关联关系，才能进入个人派单流程。

### 1.3 第一期交付范围

| 范围 | 必须交付 |
| --- | --- |
| 人员与厂商 | 厂商档案、个人账号、组织及系统协作授权、邀请激活、到期与撤权 |
| 派单管理 | 逐项或批量派单、改派、截止时间、对外材料确认、未分派提示 |
| 执行工作台 | 我的任务、任务详情、接收、沟通、进展、提交修复、延期与改派申请 |
| 审核复测 | 组织确认、集团逐项复测、逐项退回、提交版本留存、主工单汇总与关闭 |
| 权限与审计 | 任务级访问、评论及附件可见范围、下载鉴权、撤权、通知隔离、审计 |
| 兼容 | 存量工单继续使用原流程，新工单可显式启用个人派单流程 |

第一期不建设厂商团队管理、任务自由转交、跨厂商转包、代码仓库集成、自动判定修复、通用流程设计器或复杂 SLA 引擎。

## 3. 核心对象与业务约束

### 3.1 对象关系

| 对象 | 作用 | 关系 |
| --- | --- | --- |
| 漏洞 `security_findings` | 记录安全问题及最终处置结果 | 保留现有资产、系统、责任组织归属 |
| 主工单 `security_work_orders` | 组织整改责任、集团期限及总体进展 | 一个工单关联多个漏洞 |
| 修复任务 `remediation_tasks` | 指定个人执行一个漏洞的整改 | 关联主工单及其中一个漏洞 |
| 修复提交 `remediation_submissions` | 冻结一轮修复结果及证据 | 一个任务可有多轮提交 |
| 审核记录 `remediation_reviews` | 记录组织确认及集团复测 | 指向具体提交版本 |
| 协作授权 `remediation_grants` | 确定某人可接受哪些组织、系统的派单 | 不直接授予漏洞读取权限 |
| 厂商 `vendors` | 表达公司归属 | 不作为资产责任组织，不进入集团组织树 |

### 3.2 必须保持的约束

1. 任务的责任组织必须等于主工单和漏洞的责任组织。
2. 任务关联的漏洞必须已属于该主工单，且系统属于该责任组织。
3. 每个个人派单工单中的漏洞最多存在一个未取消的修复任务；改派复用任务并保留历史。
4. 当前负责人必须为有效账号，并具有匹配组织、系统且未过期的协作授权。
5. 任务内部截止时间不得晚于主工单期限；计划合作到期时间不得早于任务期限。
6. 一项任务只能存在一个当前提交版本；复测决定必须指向该版本。
7. 厂商、人员和任务归属变更不得修改既有操作记录中的历史身份快照。
8. 取消任务、撤销账号或终止合作不改变漏洞的修复结果。
9. 主工单最终关闭必须检查全部关联漏洞，不能只检查已分派的任务。
10. 列表、统计、搜索和下载均按实际授权过滤，不能先分页再过滤。

## 4. 身份、角色与授权

### 4.1 角色职责

| 角色 | 数据范围 | 允许动作 | 禁止动作 |
| --- | --- | --- | --- |
| 集团安全人员 | 现有集团安全角色授权范围 | 下发主工单、读取进度、集团复测、处置漏洞、关闭主工单 | 无有效权限时操作集团外数据 |
| 组织整改管理员 | 授权组织及系统范围 | 接收、分派、改派、督办、组织确认、申请主工单延期 | 执行集团复测、替集团接受风险 |
| 内部执行人员 | 当前明确分配的任务 | 接收、进展、沟通、上传、提交、提出申请 | 查询组织全部漏洞、自行改派、确认已修复 |
| 外部执行人员 | 当前分配且合作授权有效的任务 | 与内部执行人员相同的任务动作 | 查看集团台账、其他人员任务、内部评论和附件 |

组织整改管理员默认由现有组织管理员兼任，也可通过专用权限授予其他组织岗位。集团管理员保留现有平台管理能力；实际操作仍记录操作者及原因。

### 4.2 建议新增权限

| 权限 | 作用 |
| --- | --- |
| `remediation.assign` | 分派、改派、取消执行任务 |
| `remediation.review` | 组织确认或退回修复提交 |
| `remediation.people.manage` | 管理组织范围内的执行人员协作授权 |
| `remediation.execute` | 对本人任务执行接收、更新、提交等动作 |
| `vendor.manage` | 管理厂商档案及组织合作关系，仍受范围约束 |

集团复测继续校验现有集团安全角色和 `security_workorder.manage` 权限，并增加任务、提交版本及状态检查。

执行角色不能通过现有全局角色赋值路径获得 `data_scope=all`。应显式建模执行资格与协作授权，不向仅用于修复的账号授予 `organization` 或 `organization_and_descendants` 台账范围。所有现有默认首页、会话初始化和组织必填校验需要适配无普通组织任职的执行账号。

### 4.3 授权判定

执行端读取任务应同时满足：

1. 账号启用、登录会话有效。
2. 当前用户为任务负责人。
3. 用户有执行资格及有效的组织、系统协作授权。
4. 对外提供的材料版本仍有效。
5. 任务及关联组织、系统没有导致访问失效的停用状态。

写入动作还必须通过对应状态检查。已完成或已取消任务在授权仍有效时仅可读取；授权撤销后，执行人员也不能访问历史任务，内部管理端继续保留记录。

组织管理员操作应使用动作权限与对应组织范围的联合判断，不能将“在 A 组织有操作权限”和“可以读取 B 组织”拼成对 B 组织的操作授权。

### 4.4 账号与厂商生命周期

- 厂商档案由授权管理员登记；集团维护全局档案，组织侧只查询与自身合作相关的厂商信息。
- 内部管理员创建人员或发送邀请。外部邀请绑定组织、系统、厂商、有效期和内部责任人。
- 邀请令牌只存哈希，限定用途、时效、单次使用；重复接受不得重复创建授权。
- 已有账号可在认证后接受新组织邀请，不能仅凭填写邮箱直接合并身份。
- 组织管理员管理协作关系；对跨组织共用账号不能擅自重置密码、修改全局身份或整体停用。
- 合作终止立即撤销对应授权。全局账号停用及密码重置使用平台账户管理或本人流程。
- 任务不能因人员离职而删除，未完成任务标记为需要重新分派并通知组织管理员。
- 到期校验在每次请求执行，定时任务仅负责提醒、汇总和标记，不作为撤权生效的唯一机制。

## 5. 业务流程与状态

### 5.1 正常流程

1. 集团创建并下发主工单，选择个人派单模式。
2. 组织管理员接收工单，补齐漏洞的业务系统关联。
3. 管理员选择漏洞、具体人员、任务期限，检查并确认接收人可见材料。
4. 系统创建修复任务，向指定人员发送站内消息。
5. 执行人员接收任务，填写预计完成时间，更新进度及阻塞情况。
6. 执行人员提交修复结果，系统冻结提交版本和所引用附件。
7. 组织管理员确认材料及目标环境部署情况，通过后进入集团复测队列；不通过则说明原因并退回。
8. 集团安全人员逐项复测，通过则将对应漏洞标为已修复，失败则退回相应任务。
9. 主工单满足关闭条件后，由集团安全人员确认关闭。

### 5.2 修复任务状态

| 状态 | 中文 | 可执行动作及转移 |
| --- | --- | --- |
| `pending_acceptance` | 待接收 | 负责人接收 → `in_progress`；管理员改派或取消 |
| `in_progress` | 修复中 | 更新进度、沟通；提交 → `pending_org_review`；管理员改派或取消 |
| `pending_org_review` | 待组织确认 | 通过 → `pending_security_review`；退回 → `in_progress`；负责人按条件撤回 |
| `pending_security_review` | 待集团复测 | 修复通过或获批其他处置 → `completed`；复测退回 → `in_progress` |
| `completed` | 已完成 | 只读，记录完成原因；新发现或风险到期按重新处置规则处理 |
| `cancelled` | 已取消 | 只读，必须记录取消原因，不自动改变漏洞状态 |

完成原因 `completion_reason` 至少区分 `verified_fixed`、`risk_accepted`、`false_positive`。界面分别展示“复测通过”“已接受风险”“确认为误报”，统计中不得全部算作修复成功。

“逾期”“被退回”“存在阻塞”“延期申请中”“需要重新分派”作为独立标记或关联记录，不扩展为大量组合状态。退回记录必须保留来源、原因、时间及对应提交版本。

### 5.3 主工单状态兼容

主工单新增 `execution_mode`：`organization` 表示原组织整改流程，`individual` 表示本方案流程。保留现有主工单状态枚举。

个人派单模式的主工单投影规则：

- 草稿及已下发状态沿用现有流程；组织接收后进入 `in_progress`。
- 存在未分派、修复中、待组织确认或需要重新分派项时，主工单保持 `in_progress`。
- 所有未完成项均进入集团复测，且没有未分派项时，主工单可显示 `pending_verification`。
- 存在部分待复测项时，即使主工单仍为 `in_progress`，集团也可以逐项复测。
- 退回通过任务标记和数量展示；个人派单模式不依赖主工单 `returned` 表达逐项退回。
- 全部关联漏洞均为已修复或有当前有效的获批处置、没有活动提交和未处理任务时，提供“关闭主工单”。
- 关闭操作事务内重新校验条件，只更新主工单状态，不批量把漏洞改成已修复。
- 主工单列表增加待分派、修复中、待组织确认、待集团复测、修复通过、其他处置数量。

个人派单模式下禁用旧版主工单级“提交整改”和“整体复测通过”入口；旧 API 必须返回业务冲突，不能只隐藏前端按钮。

### 5.4 逐项复测与提交版本

- 允许一张工单 8 项通过、2 项退回，通过的记录保持有效。
- 每轮提交保存修复说明、变更或版本编号、目标环境、部署状态与时间、自测结果、附件清单。
- 组织审核与集团复测必须引用具体 `submission_id`。
- 提交后内容不可原地修改。组织审核前允许本人撤回，撤回后重新提交生成新版本。
- 与组织确认并发的撤回，以事务内状态和版本检查决定；已进入集团复测只能由集团退回后重新提交。
- 新提交不覆盖旧证据和旧复测结果；审核界面默认展示当前版本，可查历史。
- 修复验证通过应确认目标环境和版本；仅完成代码修改但未部署不能作为目标环境已修复的结论。
- 组织管理员代执行人员录入时必须显式记录“代提交”及原因；不得伪造执行人员身份。默认第一期仅支持负责人本人提交。

### 5.5 改派、延期及特殊处置

| 情况 | 处理规则 |
| --- | --- |
| 归属不正确 | 执行人员提出改派申请，原负责人保持责任；管理员确认后变更负责人 |
| 改派 | 通常只允许待接收或修复中；待审核任务应先由对应审核方退回。保留历史、撤销旧负责人访问，新负责人重新接收 |
| 授权失效 | 立即阻止执行人员访问，未完成任务提示管理员。已提交版本仍可由内部审核；如需修改，先恢复授权或退回改派 |
| 修复受阻 | 记录原因、依赖方、预计解除时间；不自动暂停期限 |
| 延期 | 记录原因、临时缓解措施、新期限。组织管理员可在主工单期限内批准；超过主工单期限须集团批准 |
| 疑似误报 | 执行人员提出并附证据，集团安全人员确认；未批准前不改变漏洞状态 |
| 无法修复或风险接受 | 提出申请，使用现有集团风险处置权限批准；临时接受风险必须有到期时间 |
| 取消修复任务 | 记录原因，漏洞仍待处置；主工单显示待重新分派。取消任务不等于取消主工单 |
| 取消主工单 | 集团执行，事务内停止所有未完成任务及待审提交，保留历史；已验证结果不被反向覆盖 |
| 风险接受到期 | 生成复核待办，不能继续计为当前有效处置。已关闭主工单不篡改历史，恢复必要的漏洞处置状态后建立新一轮工单 |
| 已修复漏洞再次发现 | 由集团确认复发，关联历史形成新一轮处置；不覆盖旧修复提交和已关闭工单 |
| 系统或资产归属调整 | 重新校验任务授权，阻止旧授权继续访问；管理员明确处理未完成任务，禁止静默迁移给新组织或厂商 |

风险接受、误报确认与修复验证应使用统一的逐项处置入口或公共事务服务，确保漏洞结果、任务完成原因和主工单汇总一致。活动任务存在时，原漏洞修改接口不得绕过该联动。

## 6. 页面与交互

### 6.1 登录及导航

- 复用现有登录及密码策略，提供 `/repair` 作为修复工作台入口。
- 仅有执行权限的账号登录后进入 `/repair/tasks`。
- 同时具有管理和执行权限的账号可切换管理工作台、修复工作台；切换视图不产生权限。
- 执行端导航只有“我的任务”“消息中心”“账户设置”。
- 复用现有强制修改初始密码流程，返回路径只接受站内允许地址。
- 修复工作台入口不等于新增互联网暴露授权；外部接入使用现有部署网络或受控接入方案，具体部署另行配置。

### 6.2 管理员派单页

入口：安全工单详情的“修复任务”页签。

列表字段：漏洞编号、标题、业务系统、严重程度、当前负责人、厂商、任务状态、期限、最近进展、审核反馈。

派单步骤：

1. 勾选未分派漏洞；支持按系统、严重程度筛选。
2. 选择具体人员。候选列表仅包含覆盖所选组织、系统且授权有效的人员；不同系统无共同候选人时提示分组派发。
3. 设置内部期限和补充要求，显示主工单期限。
4. 预览接收人可见的漏洞描述、资产地址、复现步骤、截图和附件。
5. 确认派发，展示逐项成功或失败结果；失败项保留选择，便于修正重试。

候选人员展示姓名、内部/外包、厂商、授权到期日、当前组织授权范围内的未完成任务数。不得泄露其在其他组织的工作量或合作信息。

管理员常用筛选：未分派、未接收、被退回、待我确认、临期、逾期、授权失效。统计并入筛选区，沿用现有“筛选卡＋数据表卡”布局。

### 6.3 执行人员我的任务

字段：任务编号、漏洞标题、业务系统、责任组织、严重程度、当前状态、截止时间、最近反馈。

- 默认展示未完成任务；支持待接收、修复中、被退回、待审核、已完成筛选。
- 默认先显示退回或逾期任务，其次按期限和严重程度排序。
- 跨组织账号只汇总明确分配且授权有效的任务。
- 空状态说明当前无任务；不能暴露所在组织有多少未分派漏洞。
- 已失效通知进入详情时显示“任务不存在或当前无权访问”，不泄露原任务标题。

### 6.4 任务详情

| 区块 | 内容 |
| --- | --- |
| 概况 | 标题、编号、严重程度、组织、系统、负责人、期限、当前处理环节 |
| 漏洞材料 | 已批准共享的描述、受影响地址或组件、复现步骤、证据、修复建议 |
| 验收要求 | 目标环境、部署要求、自测要求、集团修复期限 |
| 修复提交 | 修复说明、版本或变更编号、部署状态及时间、自测结果、附件 |
| 审核反馈 | 当前版本的组织意见、集团复测结果、退回原因 |
| 沟通与记录 | 对当前用户可见的评论和操作时间线 |

主按钮按状态展示“接收任务”“提交修复”“重新提交”。待审核时说明正在等待谁处理，历史提交只读。

提交修复字段：

| 字段 | 校验 |
| --- | --- |
| 修复说明 | 必填，描述实际修改及影响 |
| 部署状态 | 必填：仅代码修改、已部署测试环境、已部署目标环境；不涉及部署需说明原因 |
| 目标环境 | 必填，管理员设置验收目标；执行人员不能静默更换 |
| 自测结果 | 必填，描述验证步骤及结果 |
| 版本或变更编号 | 适用时必填；配置类修复可填写变更编号 |
| 部署时间 | 声明已部署时必填 |
| 证明附件 | 按任务要求校验，不强制所有漏洞都必须有截图 |

仅代码修改且验收要求为目标环境复测时，只能保存进展，不能提交最终修复。无需部署的任务由管理员明确设置验收方式。

### 6.5 组织确认和集团复测

- 组织待办展示本人有审核权限的提交，支持查看版本差异与证据。
- 组织通过前确认材料完整及部署声明；退回必须填写具体原因。
- 集团待办按修复任务查询，不依赖整张主工单进入待复测。
- 集团通过必须填写复测结果、验证环境及时间；失败必须填写可执行的退回说明。
- 第一期允许批量选择任务进入审核，但每项仍保存独立决定与版本，不提供无证据的一键全通过。

## 7. 材料可见性与附件

### 7.1 对外材料

任务保存经管理员确认的共享材料版本，至少包含必要的漏洞标题、严重程度、系统及受影响位置、复现步骤、修复建议、验收条件和共享附件。

执行端读取共享材料，不能直接拼接完整漏洞详情、主工单描述或测试报告。主工单编号可以作为上下文显示，但不得提供可越权打开主工单的链接。

原漏洞信息更新时，标记“共享材料待复核”，管理员确认后发布新版本。影响修复目标或验收条件的重大变化需使当前提交失效并退回，记录原因；不能对已提交版本悄悄替换验收标准。

### 7.2 评论与附件可见范围

| 范围 | 可读者 | 创建规则 |
| --- | --- | --- |
| `participants` | 当前负责人及有管理权限的内部人员 | 执行人员只能创建此范围内容；内部人员发送前明确确认 |
| `internal` | 授权内部管理人员 | 仅内部人员可创建，默认内部备注采用此范围 |

共享材料、任务评论、审核公开反馈和内部审核备注应显式分离。内部备注不能通过操作事件的 `details`、导出、通知摘要或搜索结果间接返回执行端。

### 7.3 文件规则

- 文件使用随机存储名，禁止静态公开路径直接读取；每次下载重新检查任务与可见范围。
- 上传沿用现有文件大小和类型限制，并补齐危险类型检查及安全下载响应头。
- 附件只能关联当前用户有写权限的任务；提交时验证附件确实属于该任务。
- 已被提交版本引用的附件不可物理删除或替换；错误材料通过新版本更正。
- 改派与撤权后旧链接失效，已下载副本无法撤回，因此派发前必须确认内容范围。
- 文件下载完成后记录审计；列表接口只返回授权可见的文件元数据。
- 采用流式上传时，最终落库前再次检查授权及任务版本，处理上传期间发生的改派。

## 8. 数据模型建议

以下为逻辑表设计。实际迁移序号在开发时根据仓库最新迁移确定，不预占 `00051`。

| 表或扩展 | 关键字段 | 说明 |
| --- | --- | --- |
| `vendors` | `id, name, status, created_by, created_at` | 厂商全局档案，停用不删除历史 |
| `vendor_memberships` | `vendor_id, user_id, status, valid_from, valid_until` | 个人与厂商的归属；不授予任务权限 |
| `remediation_grants` | `id, user_id, organization_id, business_system_id, vendor_id?, participant_type, status, valid_from, valid_until, sponsor_user_id` | 一条授权对应一个具体系统；外部授权期限必填，校验厂商成员关系 |
| `remediation_invitations` | `id, token_hash, inviter_id, organization_id, intended_identity, grant_payload, expires_at, accepted_at, revoked_at` | 邀请接受时重新校验邀请方权限及授权范围 |
| `security_work_orders` 扩展 | `execution_mode` | 默认 `organization`，新流程使用 `individual` |
| `remediation_tasks` | `id, task_no, work_order_id, finding_id, organization_id, business_system_id, assignee_user_id, grant_id, status, completion_reason?, due_at, current_submission_id?, version, created_by, created_at, updated_at` | `version` 用于并发控制；组织和系统冗余需保持一致 |
| `remediation_assignment_history` | `task_id, from_user_id?, to_user_id, actor_id, reason, identity_snapshot, created_at` | 保存派单、改派及当时厂商信息 |
| `remediation_material_versions` | `id, task_id, revision, approved_by, shared_payload, created_at` | 存储共享材料版本，内容采用明确字段白名单 |
| `remediation_submissions` | `id, task_id, revision, material_version_id, author_id, remediation_summary, deployment_status, target_environment, change_reference, deployed_at?, self_test_result, lifecycle_status, submitted_at` | 内容不可变；`lifecycle_status` 表达当前、撤回、退回、结束 |
| `remediation_reviews` | `id, submission_id, stage, decision, public_feedback, internal_note?, reviewer_id, reviewed_at` | `stage` 区分组织确认和集团复测；决定后不可覆盖 |
| `remediation_comments` | `id, task_id, author_id, visibility, body, created_at` | 第一版允许追加更正，不静默编辑历史评论 |
| `remediation_attachments` | `id, task_id, visibility, storage_key, original_name, content_type, size_bytes, uploaded_by, created_at` | 文件元数据；不复用主工单附件的自动可见规则 |
| `remediation_submission_attachments` | `submission_id, attachment_id` | 固定提交版本证据集合 |
| `remediation_material_attachments` | `material_version_id, attachment_id` | 固定共享材料附件集合 |
| `remediation_requests` | `id, task_id, type, status, reason, proposed_due_at?, decision, decided_by?, decided_at?` | 改派、延期、误报、风险处置申请；最终处置仍由对应领域服务执行 |
| `remediation_task_events` | `id, task_id, actor_id, action, from_status, to_status, visibility, details, created_at` | 审计事件与用户时间线分开序列化 |
| 工单期限变更记录 | `work_order_id, old_due_at, new_due_at, reason, approved_by, created_at` | 保留原始承诺及延期历史，不只覆盖 `due_at` |

索引及约束要求：

- 对 `(work_order_id, finding_id)` 建立适用于未取消任务的唯一约束，防止重复派单。
- `(task_id, revision)` 在提交版本、共享材料版本各自唯一。
- 对负责人、状态、期限，以及组织、系统、状态建立查询索引。
- 外键尽量使用限制删除；账号或厂商停用保留历史。
- `grant_id` 必须对应负责人、组织、系统及人员类型，不能只校验授权记录存在。
- 不直接信任客户端提交的组织、厂商、负责人显示名和完成原因；由服务端校验、派生或写入快照。
- 不把完整内部漏洞对象放入共享 JSON；明确允许字段并限制大小。

## 9. 接口契约

建议在 `/api/v1` 下新增专用资源。下列路径保留最初设计目标；实际已实现路径见第 16.3 节。

### 9.1 管理端

| 方法与路径 | 用途 | 主要权限 |
| --- | --- | --- |
| `GET/POST /vendors` | 查询、登记厂商 | `vendor.manage` 及组织合作范围 |
| `PATCH /vendors/:id` | 维护厂商档案 | 平台范围档案权限；组织合作信息单独维护 |
| `GET/POST /remediation-grants` | 查询、新增协作授权 | `remediation.people.manage`＋组织范围 |
| `PATCH /remediation-grants/:id` | 延长、停用或撤销授权 | 同上，记录原因 |
| `POST /remediation-invitations` | 创建邀请 | 同上 |
| `POST /remediation-invitations/accept` | 接受邀请或激活账号 | 有效邀请证明及身份校验，不依赖管理权限 |
| `GET /security-work-orders/:id/remediation-tasks` | 主工单任务列表及汇总 | 对应组织或集团管理权限 |
| `GET /security-work-orders/:id/assignee-options` | 查询可派人员 | `remediation.assign`＋组织范围，按所选系统交集过滤 |
| `POST /security-work-orders/:id/remediation-tasks:batch-assign` | 批量派单 | `remediation.assign` |
| `POST /remediation-tasks/:id/reassign` | 改派 | `remediation.assign`，要求当前版本及原因 |
| `POST /remediation-tasks/:id/cancel` | 取消执行任务 | `remediation.assign`，校验状态及原因 |
| `GET /remediation-reviews` | 当前角色的待审核列表 | 组织确认或集团复测权限 |
| `POST /remediation-submissions/:id/organization-review` | 组织通过或退回 | `remediation.review`＋任务组织范围 |
| `POST /remediation-submissions/:id/security-review` | 集团复测通过或退回 | 集团安全角色及原工单管理权限 |
| `POST /remediation-requests/:id/decide` | 处理申请 | 按申请类型校验组织或集团权限 |
| `POST /security-work-orders/:id/extend-deadline` | 集团调整主工单期限 | 集团工单管理权限 |

### 9.2 执行端与共享任务接口

| 方法与路径 | 用途 |
| --- | --- |
| `GET /repair/tasks` | 本人任务列表与筛选 |
| `GET /repair/tasks/:id` | 受限任务详情及共享材料 |
| `POST /repair/tasks/:id/accept` | 接收任务 |
| `POST /repair/tasks/:id/progress` | 更新进度及阻塞说明 |
| `POST /repair/tasks/:id/submissions` | 创建并提交新修复版本 |
| `GET /repair/tasks/:id/submissions` | 查询当前及历史版本的可见内容 |
| `POST /repair/tasks/:id/submissions/:submission_id/withdraw` | 组织审核前撤回当前版本 |
| `GET/POST /repair/tasks/:id/comments` | 查询或追加可见评论 |
| `POST /repair/tasks/:id/attachments` | 上传修复证据 |
| `GET /repair/tasks/:id/attachments/:attachment_id/download` | 鉴权下载 |
| `POST /repair/tasks/:id/requests` | 提交改派、延期、误报等申请 |

管理端可以使用对应管理资源访问相同领域服务，但执行端响应必须使用独立 DTO，禁止直接复用包含内部字段的管理端对象。

### 9.3 通用规则

- 分页遵循现有 `page / page_size / total / items` 契约，默认 20、最多 100。
- 批量派单上限 100 项；逐项事务、逐项结果，每项返回漏洞 ID、任务 ID 或稳定错误码。
- 相同负责人覆盖多个系统时逐项重新校验，不能依据前端候选列表省略服务端验证。
- 关键写入携带 `expected_version`；冲突返回 HTTP 409，前端提示刷新后重试。
- 派单和提交支持幂等键。同键同请求返回既有结果，同键不同内容返回冲突；批量请求按项保存处理结果，重试不能重复派发。
- 接口无认证返回 401，无动作权限返回 403，状态/版本/重复分派冲突返回 409。
- 对执行端越权资源使用与不存在资源一致的 404 响应，防止枚举；错误文案不包含内部名称。
- 按现有错误格式返回稳定业务码，如 `grant_expired`、`invalid_transition`、`version_conflict`、`finding_already_assigned`。
- 取消、改派、组织审核、集团复测、延期和材料更新都记录原因或业务结果。

## 10. 一致性、并发与后端组织

建议新增 `backend/internal/remediation` 与 `backend/internal/vendor`，在 `httpserver` 注册管理端及执行端路由。任务访问和转换规则集中实现，不在多个 HTTP handler 中分别拼装。

关键操作事务内完成：

1. 按统一顺序锁定主工单、漏洞、任务及当前提交，避免关闭与逐项复测互相竞争。
2. 重新校验账号、动作权限、当前负责人和有效授权；任务创建时还校验组织、系统和材料范围。
3. 校验状态、版本及幂等记录。
4. 更新任务、漏洞处置、提交生命周期及主工单汇总所需数据。
5. 写入审核、事件、审计及通知事件。
6. 提交事务后再触发非事务性消息投递。

授权撤销与任务写入需采用兼容的锁顺序或版本检查，避免已撤权操作仍成功。上传文件可先放临时区，授权验证和元数据提交失败则清理临时文件。

通知可扩展现有事务内事件机制；发送失败不能回滚已完成的业务动作，应持久化待发送事件并可重试、去重。

## 11. 通知、审计与统计

### 11.1 通知

| 事件 | 接收人 |
| --- | --- |
| 派单、改派 | 新负责人及组织管理员；旧负责人只收到不含敏感详情的变更提示 |
| 提交修复 | 有组织审核权限的责任人员 |
| 组织确认通过 | 集团复测人员及提交人 |
| 组织或集团退回 | 当前负责人及组织管理员 |
| 复测通过 | 当前负责人及组织管理员 |
| 临期或逾期 | 当前负责人及组织管理员，按节点去重 |
| 合作授权即将到期或已失效 | 内部责任人及组织管理员 |
| 延期、改派等申请结果 | 申请人；读取时检查现行授权 |

第一期临期节点可默认沿用现有工单习惯，在到期前 3 天提醒一次，到期后按配置频率汇总。消息查询及未读计数均排除当前已无权读取的任务内容，通知链接不能恢复权限。

### 11.2 审计

必须记录开户或邀请、授权变更、派单、材料发布、改派、接收、提交、撤回、审核、下载、延期、取消、主工单关闭和越权失败等关键动作。

审计字段包含操作者、责任组织、资源、动作、旧值及新值摘要、时间、请求 ID；不得将密码、邀请原始令牌或完整敏感证据写入日志。

### 11.3 统计口径

- 修复通过数量只计 `verified_fixed`，风险接受与误报单独统计。
- 分别记录首次派单、接收、每轮提交、组织确认、集团复测时间。
- 区分执行耗时、组织等待时间、集团复测等待时间。
- 同时保留原始期限与批准后的期限，避免延期覆盖历史逾期事实。
- 厂商或人员工作量统计受查询者组织范围限制。
- 不设置未经定义的“进度百分比”；优先展示已复测通过数量及各环节数量。

## 12. 存量兼容与上线策略

1. 新增表及字段，历史主工单默认 `execution_mode=organization`。
2. 原组织模式工单继续采用原接口及行为；不自动生成个人任务，不回写历史修复记录。
3. 新建主工单可选择个人派单模式；第一期不支持已进入整改的存量工单在线切换模式。
4. 先完成后端动作授权和执行账号适配，再开放外部人员登录入口。
5. 用一个组织及少量内部账号试运行，验证派单和逐项复测，再启用外部邀请。
6. 试运行中关闭新功能入口只停止新邀请和新派单，已有任务仍需可完成；不能通过隐藏入口留下无法处理的活动任务。
7. 一旦产生个人派单数据，不能只回滚前端或数据库迁移至旧代码。回滚方案应停止新写入、保留数据和兼容服务，必要时按现有备份恢复流程另行处理。
8. 更新备份验证，使新增表及附件目录纳入现有备份与恢复检查。

外部接入前，应验证旧的资产、漏洞、工单、组织、用户、导出、通知接口对执行账号均没有额外授权；不能只测试 `/repair` 路由。

## 13. 开发拆分与完成标准

| 阶段 | 开发内容 | 完成标准 |
| --- | --- | --- |
| A：身份及授权 | 厂商、协作授权、邀请、执行账号登录、独立任务授权 | 无管理角色账号能登录且无法读取组织台账；撤权即时生效 |
| B：派单及材料 | 任务模型、批量派单、候选人员、共享材料、改派 | 任务与漏洞、组织、系统一致；重复及越权派单被拒绝 |
| C：执行工作台 | 我的任务、详情、沟通、证据、接收、提交及撤回 | 修复结果按版本保存；执行人员只能访问本人任务 |
| D：审核闭环 | 组织确认、逐项集团复测、其他处置、主工单关闭、申请处理 | 部分通过部分退回正确；旧接口无法绕过新流程 |
| E：运营及验收 | 定向消息、到期提醒、审计、统计、存量回归、备份恢复 | 完整角色回归及跨组织隔离通过，文档与交付行为一致 |

A—E 共同构成第一期完整交付。不能以只增加登录页、角色或任务列表作为第一期完成。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| C01 | 双击派单或重试相同请求 | 不产生重复任务，幂等结果一致 |

| C06 | 主工单取消或关闭与任务复测并发 | 不出现已取消任务继续流转或未完结漏洞被关闭 |

### 16.2 实际数据结构与设计映射

- `00051_remediation_workspace.sql`：新增厂商、协作授权、邀请、个人任务、材料版本、提交、审核、沟通、附件、申请、事件与幂等记录；主工单增加 `execution_mode`，默认 `organization`，个人模式为 `individual`。
- `00052_remediation_integrity.sql`：对当前系统/资产归属再次校验；个人任务管理中的漏洞增加数据库写入保护，旧漏洞 API 不能绕过任务审核直接改状态。
- 厂商采用**责任组织内合作档案**，同一厂商在不同组织可各自建档；人员归属通过 `remediation_grants` 关联账号、组织、系统与厂商。第一期没有建立全集团唯一厂商主数据或独立的厂商成员表。
- 改派历史、材料修订、期限变更及处置写入任务事件和审计日志；没有另建每一种变化的历史表。
- 修复提交与附件通过关系表绑定，保留材料版本及审核记录；不提供删除历史证明附件的 API。
- 站内消息从持久化事件和当前任务状态读取，并实时检查可见权限；第一期没有接入邮件、企业消息或异步通知队列。
- 派单/提交支持幂等键，状态变化要求 `expected_version`；写事务使用统一 PostgreSQL advisory lock 和行锁串行处理。这一实现优先保证第一期正确性，高并发场景可再细化锁粒度。

### 16.3 当前 API 映射

所有地址以 `/api/v1` 为前缀；与第 9 节中的概念接口有差异时，以此表和 `backend/internal/httpserver/remediation.go` 为准。

| 方法与地址 | 说明 |
| --- | --- |
| `GET /remediation-options` | 当前可管理的系统与组织选项 |
| `GET/POST /vendors`、`PATCH /vendors/:id` | 组织内厂商列表、创建、修改/停用 |
| `GET/POST /remediation-grants`、`PATCH /remediation-grants/:id` | 人员开通与授权、延期/撤销 |
| `GET/POST /remediation-invitations`、`POST /remediation-invitations/:id/revoke` | 邀请列表、创建、撤销 |
| `POST /repair-invitations/accept`、`POST /repair-invitations/accept-existing` | 新账号激活、已登录本人接受邀请 |
| `GET /security-work-orders/:id/remediation-summary` | 汇总、未分派数、各任务状态数量 |
| `GET /security-work-orders/:id/assignable-findings` | 可派发漏洞及材料预览 |
| `POST /security-work-orders/:id/remediation-tasks/batch-assign` | 批量派发，最多 100 项，返回逐项结果 |
| `POST /security-work-orders/:id/close-individual` | 全部逐项处置后关闭个人模式主工单 |
| `GET /repair/tasks`、`GET /repair/tasks/:id` | 执行人员任务列表/详情 |
| `GET /remediation-tasks`、`GET /remediation-tasks/:id` | 管理端任务列表/详情 |
| `GET {task}/comments\|events\|attachments\|submissions\|requests` | 分页读取任务子资源 |
| `POST {task}/actions/:action` | 接收、进展、提交、撤回、审核、改派、取消、材料修订、恢复整改 |
| `POST {task}/requests`、`POST /remediation-requests/:id/decide` | 提出及审批申请 |
| `POST {task}/attachments`、`GET {task}/attachments/:attachmentID/download` | 附件上传与鉴权下载 |

`{task}` 可为 `/repair/tasks/:id` 或 `/remediation-tasks/:id`。具体 action 为 `accept`、`progress`、`comment`、`submit`、`withdraw`、`organization-review`、`security-review`、`reassign`、`cancel`、`materials`、`reopen-risk`。执行端前缀不能调用管理员操作。

派单及修复提交要求 `Idempotency-Key` 请求头。详情采用 `{item: ...}`，分页采用 `{items,total,page,page_size}`；主要错误码为 `invalid_request`（400）、`forbidden`（403）、`not_found`（404）、`state_conflict`（409）。无权限读取任务统一按不存在处理。

附件单文件上限 20 MB，允许 PNG/JPEG/PDF/TXT/LOG/CSV/ZIP/XLSX/DOCX，执行人员只能上传参与者可见文件；下载强制鉴权、attachment 响应、禁止缓存。图片/PDF验证文件签名，不接受识别为 HTML/脚本的证明材料。

### 18.2 新增 API 与字段

仍以 `/api/v1` 为前缀，沿用第 16.3 节响应格式及版本、幂等要求。

| API | 权限及用途 |
| --- | --- |

统计时间以持久化状态事件累计，包括重复修复与退回；进行中的阶段统计至查询时间。执行耗时包含待接收，界面明确展示这一口径。全部统计与当前筛选一致，执行端切换“全部状态”才能看到历史完成数。逾期汇总按固定时间周期去重，不使用异步发送队列；读取失败后重试同一持久化事件不会重新生成一条业务事件。
