## 0. 本轮结论与后续执行口径

### 0.1 结论

资产和漏洞是系统的两条主线，安全工单是漏洞整改的执行闭环，不能再用一个笼统的“组织可见/状态”覆盖三者的不同职责：

```text
资产：谁对资产事实负责，谁确认；谁有发布权限，谁发布
漏洞：安全人员判断风险和状态，组织负责确认归属和整改
工单：按动作授权执行，整改材料按任务授权，复核与关闭必须分离
```

因此，本轮不删除草稿箱、不强制漏洞必须先有测试批次或正式资产，也不允许用前端隐藏按钮代替后端授权。`IP:PORT` 继续归类到 IP 资产，端口保留在服务/发现位置字段中。

### 0.2 当前执行阶段

批次 A（安全边界止血）已经完成核心服务层改造，当前不是重新设计阶段，而是**补齐接口级验收和收口残余读取边界**：

- 已增加安全工单 `view/execute/assign/review/close` 五类动作权限；
- 已将旧工单动作授权从“组织可见”拆开；
- `individual` 工单的旧推进、提交、复核、关闭路径由服务端拒绝，并返回明确的 409 语义；
- 已修复未授权取消 individual 工单可能先产生整改任务副作用的问题；
- 附件上传/删除已开始绑定工单动作和组织范围；
- 自我复核已有服务层和数据库完整性约束。

同时，批次 C 的草稿治理已经进入代码实施：资产草稿和业务系统草稿已接入版本号、责任人、接管字段、软删除和恢复入口，并新增迁移 `00067_inventory_draft_concurrency.sql`；本轮又补充了候选跟进记录（`00068_asset_candidate_followups.sql`）和漏洞三维状态持久化第一阶段（`00069_security_finding_state_dimensions.sql`）。后端测试已在 Podman 中验证通过，但完整接口矩阵、数据库并发场景、恢复页面、候选跟进测试和状态迁移矩阵仍未视为交付。

本轮代码基线还补上了几个容易被旁路写路径遗漏的约束：

- 草稿 CAS 失败按“草稿不存在 / 状态不可编辑 / 版本过期”区分错误语义，分别对应 404、业务状态错误和 409 冲突，而不是全部返回同一种错误；
- 选择资产、选择业务系统、启动任务、提交、退回、发布以及既有草稿 upsert 等写路径都会递增版本并记录最后编辑人；
- 资产和业务系统页面已经开始携带 `expected_version` 保存和删除草稿，前端冲突提示和刷新策略仍需验收；
- **本轮闭环的业务系统直接工作区**：`backend/internal/businesssystem` 的未上报工作版本过去完全没有乐观锁，两个填报员可以互相覆盖，一份过期的删除请求还能丢掉别人刚录入的内容。现在草稿列表与详情返回 `version`，更新/作废/下线必须携带 `expected_version`，版本随每次写入递增并同步 `last_edited_by`，缺失版本直接拒绝（400），版本落后返回 409 `working_version_conflict`，并为每次写入落审计；
- 截至本轮记录，迁移已验证到 `00069`，`make test-backend`（含 `assetcandidate`、`businesssystem` 带库集成测试）与 `make test-frontend` 已在 Podman 中针对当前工作树通过；角色边界 E2E 和镜像构建尚需重跑。
- 尚未完成五类身份的列表、详情、事件、漏洞、附件等接口完整正向/反向回归，也尚未完成恢复 UI、数据库并发、候选跟进和三维状态统计/通知口径验收。

因此，批次 A 和批次 C 仍不宣告整体完成：当前是“核心代码已落地、后端工程门禁已通过、业务验收未闭环”。迁移 `00068`、`00069` 也只代表数据模型和服务入口已经具备，不代表候选协作和状态语义已经完成产品闭环。

### 0.3.1 本轮新增结论

#### 资产候选跟进不是第二套工单

集团安全管理员需要能够对跨组织资产候选进行记录、催办和请求组织接手，但这种动作不能改变候选审核状态，也不能让安全人员取得资产确认或正式发布权限。因此新增的候选跟进记录只允许以下三类：

```text
note             记录判断或上下文
reminder         记录催办事项
handoff_request  请求责任组织接手/确认
```

跟进记录必须关联候选、操作者、时间、请求 ID 和来源 IP，并写入审计；如果后续需要责任人、截止时间、升级策略，应另行设计真正的协作任务，不能把跟进表直接膨胀成第二套工单系统。

#### 漏洞状态先拆维度，暂不破坏旧 JSON/API 兼容

迁移 `00069_security_finding_state_dimensions.sql` 新增：

| 维度 | 字段 | 当前值 | 语义 |
|---|---|---|---|
| 漏洞/风险 | 既有 `status` | `pending`、`in_progress`、`confirmed`、`resolved`、`fixed`、`false_positive`、`ignored`、`duplicate`、`risk_accepted` | 保留既有 API 和导入兼容，表示漏洞判断/风险处置语义 |
| 资产关联 | `asset_link_status` | `unlinked`、`pending`、`live`、`retired` | 表示尚未关联、已进入工作版本、已关联正式资产、正式资产已软删除 |
| 整改执行 | `remediation_status` | `not_started`、`pending_acceptance`、`in_progress`、`pending_org_review`、`pending_security_review`、`completed` | 表示整改任务的执行进度，不等于漏洞已经修复 |

当前旧 `status` 没有被删除，也没有偷偷改名为 `vulnerability_status`；后续必须补齐状态迁移矩阵、原始 JSON 状态保留、统计口径、通知文案和风险接受到期规则。

### 0.3 下一步执行顺序

按以下顺序推进，后一项不得以牺牲前一项的权限和数据一致性为代价：

1. **先验证本轮新增代码**：补齐 `00068` 候选跟进和 `00069` 三维状态的服务层、数据库和 HTTP 测试；重新在 Podman 执行前端、E2E 和构建，避免未经验证的权限/状态代码继续扩散；
2. **批次 A 收尾**：补齐集团管理员、集团安全管理员、子公司管理员、子公司填报员、外部厂商五类身份的接口级正反向测试，逐一验证旧入口不能绕过新任务模型；
3. **批次 B 主线收口**：补齐漏洞待关联联动、候选跟进、组织确认、工作版本和发布链路，打通漏洞到正式资产的追踪链；
4. **批次 C 数据可靠性收口**：完成草稿所有权、乐观锁、管理员接管、提交快照、软删除和恢复改造，并通过 Podman 数据库并发测试；
5. **批次 D 治理收口**：集团管理员紧急资产变更审计，以及漏洞/工单/整改任务的状态迁移矩阵、统计和通知口径；
6. **批次 E 外部协作**：厂商授权生命周期、脱敏和全量越权回归。

页面卡片、批量操作和统计优化必须建立在上述权限、状态和数据链稳定之后。

### 0.4 后续优先事项（执行版）

后续不按“哪个页面更容易开发”排序，而按**事故影响、数据不可逆性和主线阻塞关系**排序。当前建议直接按以下顺序排期：

| 优先级 | 先做什么 | 为什么现在做 | 交付/退出条件 |
|---|---|---|---|
| P0-1 | 新增迁移和权限代码验收 | 未验证的授权和状态代码继续扩散，会把问题带到更多入口 | `00068`/`00069` 有服务层、HTTP、数据库正反向测试；Podman 内前端测试、角色 E2E、构建和迁移通过 |
| P0-2 | 安全工单全接口权限矩阵 | 越权比功能缺失更紧急；列表、详情、附件和通知是最容易绕过动作授权的旁路 | 五类角色对列表、详情、漏洞/事件、附件、通知及 `issue/accept/progress/submit/review/close/cancel` 均有允许/拒绝用例；individual 只能走 `remediation_tasks` |
| P0-3 | 漏洞候选到正式资产闭环 | 这是“漏洞不丢、资产可归属、整改可追责”的核心业务链 | 真实脱敏 JSON 完成导入；无批次/无资产仍保留；`IP:PORT` 聚合到 IP；确认→工作版本→发布后回链 `finding.asset_id` |
| P1-1 | 资产/业务系统草稿治理收口 | 没有所有权和 CAS 会造成资产覆盖、责任不清和审核快照失真 | 所有写路径携带并校验 `expected_version`；冲突 409；接管有原因和审计；软删除/恢复可追溯；并发测试通过 |
| P1-2 | 正式资产紧急变更审计 | 集团管理员的直写能力是绕过工作版本的高风险通道 | 原因、前后快照、操作者、request ID、来源 IP、补录/复核任务齐全；核心资产有二次复核 |
| P1-3 | 漏洞三维状态语义收口 | 只增加字段而不统一语义，会导致统计、通知和页面继续混淆 | 保留旧 JSON/API；记录原始值、标准值和转换原因；明确状态迁移、风险接受到期、重复主漏洞和工作版本废弃回退规则 |
| P2 | 外部厂商生命周期与体验优化 | 依赖前述任务模型和权限边界稳定后再扩大协作范围 | grant 过期/撤销、厂商禁用、跨任务/附件隔离、脱敏和全量 E2E 通过；再做卡片、批量操作和页面体验 |

**排期原则：**

1. P0 未完成前，不新增组织级整改入口，不以“隐藏按钮”作为权限交付，不优先做只读统计卡片；
2. P1-1 与 P1-2 不能省略，否则资产主线仍存在覆盖和旁路写入风险；
3. 每个批次都要同时交付“代码 + 数据库迁移（如有）+ 接口正反向测试 + Podman 验证 + 文档状态更新”；
4. 只有通过退出条件，本文档中的“验收中/部分落地”才能改为“已完成”。

## 1. 执行摘要

当前系统已经形成了三条基本主线：

```text
资产填报 → 工作版本 → 集团审核 → 正式资产
漏洞登记 → 资产候选 → 资产工作版本 → 漏洞正式关联
安全工单 → 整改任务 → 组织复核 → 安全复核 → 关闭
```

整体方向是正确的，特别是以下设计已经具备产品基础：

- 漏洞没有正式资产时仍可以先登记，不再因为资产缺失而丢失漏洞；
- IP:PORT 可以归类到对应的 IP 资产，端口作为位置或备注信息保存；
- 资产候选可以进入组织工作版本，工作版本发布后再完成正式关联；
- 工作版本废弃后，相关漏洞可以恢复到未正式关联状态；
- 新的个人整改任务模型已经包含授权、任务、提交、组织复核和安全复核；
- 外部厂商原则上通过明确的整改授权和个人任务进行隔离。

但系统当前仍有四个结构性问题：

1. **旧安全工单把“可以访问组织”近似当成“可以执行组织工单”**。子公司填报员可能接受、推进并提交本组织旧工单，这是 P0 权限问题。
2. **集团安全管理员可以发现漏洞，却无法完整追踪对应资产候选**。漏洞导入待关联项和资产候选属于两个互不连通的权限队列，这是 P0 流程断点。
3. **资产草稿实际上是组织共享编辑区**。同组织填报员之间没有充分的草稿所有权、版本号和并发编辑保护。
4. **旧组织级工单和新个人整改任务并存**。如果不彻底隔离两套入口，细粒度授权可能被旧接口绕过。

本文件的核心原则是：

```text
组织可见 ≠ 工单可执行
工单可执行 ≠ 安全可复核
安全可复核 ≠ 资产可发布
```

## 1.1 已冻结的产品决策

本次审计不建议继续通过增加页面入口来掩盖流程边界，先冻结以下产品决策，后续代码、接口和页面都必须以此为准：

| 决策 | 结论 | 目的 |
|---|---|---|
| 资产草稿箱是否删除 | **不删除**，保留为受控的临时工作区 | 资产采集允许分阶段填写，但必须补齐所有权、版本和生命周期 |
| 漏洞导入是否必须已有测试批次/正式资产 | **不强制**。漏洞可以先进入待关联状态 | 不能因为资产台账尚未完成而丢失已经确认的安全发现 |
| `IP:PORT` 如何归类 | 以 IP 作为资产归属，端口作为服务/发现位置字段 | 避免为每个端口虚构一个资产，同时保留定位整改所需信息 |
| 集团安全管理员能否确认资产 | 可查看候选、关联漏洞、催办和跟踪；**不能代替组织确认或直接发布正式资产** | 保持安全风险判断与资产事实确认分离 |
| individual 工单走哪条整改链路 | 只能走 `remediation_tasks`；旧组织级 `Accept/Progress/Submit` 在服务端拒绝 | 防止旧接口绕过个人授权、任务分派和复核链路 |
| 集团管理员能否直写正式资产 | 暂时保留，但改造成有原因、前后快照和审计的“紧急变更” | 兼顾应急处置和数据治理，避免无痕绕过流程 |
| 漏洞状态如何展示 | 分拆为“漏洞状态、资产关联状态、整改状态”三个维度 | 避免 `resolved`、`fixed`、待关联等概念互相混淆 |

其中，**不删除草稿箱**并不等于继续保留组织共享编辑区。草稿必须变成“有归属、可接管、可并发控制、可提交快照、可恢复”的工作对象，而不是绕过正式资产流程的第二套台账。

## 1.2 后续优先级判断原则

后续事项按以下顺序判断，而不是按页面数量或开发工作量排序：

1. **先修越权和数据泄露**：任何角色能够看到或修改不属于自己的工单、任务、附件和草稿，都属于上线阻断项。
2. **再修数据一致性**：避免漏洞、资产候选、工作版本、正式资产和整改任务之间出现无法追溯的断链。
3. **再修闭环效率**：让集团安全管理员、子公司管理员和执行人员能够在同一条主线上协作。
4. **最后做体验和统计优化**：卡片、筛选、批量操作应建立在权限和状态稳定之后。

因此，后续第一个开发批次不应优先做新的统计页面，而应先完成旧工单权限收紧、individual 入口隔离、附件读取边界和自我复核阻断。

## 3. 目标职责边界

### 3.1 集团管理员

应负责：

- 组织、用户、角色和平台配置；
- 集团资产制度和流程配置；
- 资产任务创建、模板和策略；
- 紧急运维、审计和回收站管理。

不应默认承担：

- 每个漏洞的技术风险判断；
- 每个安全工单的日常整改；
- 自己创建、自己审核、自己发布的完整闭环；
- 替子公司长期维护正式资产。

集团管理员是平台治理者，不应成为所有业务的日常执行者。

### 3.2 集团安全管理员

应负责：

- 集团安全测试；
- 漏洞导入、去重和技术状态判断；
- 安全工单创建、下发和最终安全复核；
- 误报、风险接受、漏洞关闭；
- 集团安全统计、SLA 和催办。

不应直接负责：

- 正式资产台账维护；
- 子公司资产工作版本编辑；
- 资产正式发布；
- 替组织确认资产归属。

但应具备对资产候选的**协作查看和催办能力**，不能因为没有 `asset.manage` 就完全失去资产关联上下文。

### 3.3 子公司管理员

应负责：

- 本组织资产和业务系统的数据责任；
- 组织内填报任务协调和初审；
- 本组织资产候选确认；
- 个人整改任务分派；
- 组织复核整改材料。

不应负责：

- 集团范围漏洞风险接受；
- 误报确认；
- 集团最终安全复核；
- 正式资产的集团级发布。

### 3.4 子公司填报员

应负责：

- 创建、编辑和提交自己负责的资产草稿；
- 补充业务系统和资产资料；
- 执行明确分配给自己的整改任务。

不应默认拥有：

- 修改其他人员草稿的权限；
- 组织资产候选最终确认权；
- 整改任务分派权；
- 组织复核权；
- 旧组织级安全工单的任意执行权；
- 风险接受、误报确认和工单关闭权。

### 3.5 外部厂商人员

外部厂商不是一个可以访问组织全部数据的普通角色，而应通过以下链路获得最小权限：

```text
厂商成员 → 有效 remediation_grant → 指定 remediation_task
```

只能看到和操作本人有效授权对应的任务，不能访问：

- 集团漏洞池；
- 完整资产台账；
- 其他厂商或其他人员的任务；
- 组织内部备注；
- 风险接受、误报和安全复核；
- 未授权附件和扫描原文。

## 5. 按业务流程审计

## 5.1 正常资产入库

### 当前流程

```text
集团管理员创建资产填报任务
→ 子公司管理员/填报员编辑草稿
→ 质量检查
→ 子公司提交
→ 集团管理员审核
→ 工作版本发布为正式资产
```

### 当前优点

- 组织侧通常先写工作版本，不直接覆盖正式资产；
- 有质量检查、提交快照和集团审核；
- 资产和业务系统可以在同一审核发布流程中处理；
- 发布后的正式资产可以作为漏洞关联目标。

### 当前问题

#### 问题一：集团管理员可以绕过工作版本

`usesWorkingInventory()` 当前以 `group_admin` 为例外，集团管理员可以直接写正式资产。

风险：

- 普通组织必须经过任务、检查、审核，集团管理员可以绕过；
- 正式资产可能没有完整提交快照；
- 变更责任和数据质量标准不一致；
- 资产变更会影响漏洞、工单和业务系统关联。

建议：

- 默认所有常规入库都走工作版本；
- 保留“紧急直写”时，强制填写原因；
- 记录变更前后快照和审计事件；
- 对核心资产要求二次审批；
- 紧急直写后自动生成补录任务。

#### 问题二：创建、审核、发布缺少强制职责分离

当前审核主要要求集团管理员角色，没有明确限制任务创建人不能完成最终审核。

风险：

```text
同一人创建任务 → 组织提交 → 同一人审核 → 同一人发布
```

建议：

- 任务创建人不能单独完成最终审核；
- 核心资产和严重/高危漏洞关联资产强制双人复核；
- 区分资产数据审核和安全风险审核。

#### 问题三：草稿是组织共享区，不是个人草稿

`loadDraftAssignment()` 主要检查任务、组织、状态和资源权限，没有充分约束草稿所有人和当前编辑人。

风险：

- 填报员可能覆盖其他人的草稿；
- 两人并发保存时，后保存者覆盖先保存者；
- 数据错误难以归责；
- 组织管理员接管编辑没有清晰审计。

建议：

- 草稿增加版本号和乐观锁；
- 保存时提交 `expected_version`；
- 普通填报员只能编辑本人或明确分配给自己的草稿；
- 管理员接管时记录接管原因；
- 保留草稿变更历史。

## 5.2 漏洞没有正式资产

### 当前流程

```text
安全管理员导入漏洞
→ 没有正式资产
→ 形成待关联漏洞
→ 生成资产候选
→ 责任组织确认
→ 进入资产工作版本
→ 工作版本发布
→ 漏洞完成正式资产关联
```

这个流程方向正确，漏洞不应因资产暂时未入库而被拒绝。

### 当前问题：候选协作已经接通入口，但业务闭环和读取边界仍未验收

漏洞导入待关联项和资产候选已经通过候选查看/跟进权限建立连接，且新增了轻量跟进记录；但当前仍需要验证以下内容：

```text
集团安全管理员：可查看候选、关联漏洞和跟进记录，可催办/请求接手，但不能确认或发布
子公司资产人员：可查看本组织候选和完整漏洞上下文，可按职责确认并进入工作版本
```

剩余风险：

- HTTP 列表、详情、关联漏洞和跟进记录可能存在不一致的读取边界；
- 组织人员是否能从候选完整追溯漏洞证据，需要真实脱敏 JSON 回归；
- 跟进记录不能被误用成改变候选状态的隐式审批；
- 并发导入和并发确认仍需验证唯一性、幂等性和失败重试。

跨域协作视图和动作权限应保持：

```text
finding_import.view
finding_import.follow_up
asset_candidate.view
asset_candidate.confirm
asset_candidate.link
```

集团安全管理员可以查看：

- 关联漏洞数量和最高严重性；
- 责任组织；
- 候选状态；
- 是否已进入工作版本；
- 当前阻塞原因；
- 当前处理人；
- 下一步动作。

但不因此获得正式资产台账写权限。

## 5.3 旧组织级安全工单

### 当前流程

```text
集团安全管理员创建
→ 下发
→ 子公司用户接受
→ 更新进度
→ 提交整改结果
→ 集团安全管理员复核
→ 关闭
```

### P0 问题（历史缺口）：访问组织被当成执行工单

历史实现中，`Accept()`、`Progress()`、`Submit()` 最终进入 `transition()`，主要检查：

```text
access.CanAccessOrganization()
```

而不是明确的整改执行权限。

该缺口的核心服务层修复已完成，现有入口应按 `view/execute/assign/review/close` 动作权限判定。因此，以下行为作为回归测试必须保持拒绝，而不是继续视为产品能力：

- 通过组织可见性读取无关工单；
- 接受不属于本人任务的工单；
- 更新组织级进度；
- 通过旧入口提交整改结果。

建议新增并强制使用：

```text
security_workorder.view
security_workorder.execute
security_workorder.assign
security_workorder.review
security_workorder.close
```

### P0 问题（历史缺口）：individual 工单可能被旧入口干扰

个人整改任务已经有更细粒度的授权和提交模型，但旧工单接口仍然存在，容易造成：

```text
新模型控制了任务权限，旧模型却仍然提供组织级操作入口
```

当 `execution_mode = individual` 时，工单层只能负责：

```text
创建、下发、取消、查看汇总、关闭
```

具体整改必须通过：

```text
remediation_tasks
```

旧的 `Accept/Progress/Submit` 以及同类旧动作必须在服务端明确拒绝，不能只在前端隐藏按钮。该拒绝已落地，返回冲突语义；后续要补齐 HTTP、附件、通知和审计事件的回归。

### P0 问题：详情和附件读取过宽

`GetWorkOrder()` 主要依据组织访问判断详情权限，可能使组织内不负责整改的用户看到：

- 漏洞摘要；
- 资产和业务系统信息；
- 整改要求；
- 工单事件；
- 整改结果；
- 退回原因；
- 附件或安全证据。

建议普通填报员默认只访问本人任务，不自动访问组织全部安全工单。

## 5.4 新个人整改任务和外部厂商

新模型的正确主线是：

```text
安全管理员创建 individual 工单
→ 子公司管理员分派个人任务
→ 内部人员/厂商执行
→ 提交整改材料
→ 子公司组织复核
→ 集团安全复核
→ finding.fixed
→ 工单关闭
```

当前设计的优点：

- grant 绑定组织、业务系统、厂商和有效期；
- 任务只分配给明确的人员；
- 有任务版本和提交版本；
- 有组织复核和安全复核；
- 外部人员不能直接完成安全复核；
- 工单关闭时可以检查任务和漏洞是否已经闭环。

必须继续补强：

- 禁止整改提交人作为最终安全复核人；
- 防止跨 task ID、finding ID 和附件下载；
- grant 过期或撤销后立即失效；
- 厂商禁用后已有授权是否失效要明确；
- 外部人员只能提交整改材料，不能提交风险接受和误报判定；
- 内部备注、源材料和集团安全意见不得泄露。

## 5.5 状态语义

迁移 `00069_security_finding_state_dimensions.sql` 已完成第一阶段落地：旧 `security_findings.status` 继续承载漏洞/风险状态，新增 `asset_link_status` 和 `remediation_status` 分别承载资产关联、整改执行状态，并通过回填和数据库触发器保持基础同步。当前仍不能把三者合并成一个筛选或统计口径；迁移矩阵、通知和前端展示需要下一阶段补齐。

### 漏洞状态

```text
pending           待处理
in_progress       处理中
confirmed         已确认
resolved          已处理
fixed             已修复
false_positive    误报
ignored           忽略
duplicate         重复
risk_accepted     风险接受
```

### 工单状态

```text
draft
issued
in_progress
pending_verification
returned
closed
cancelled
```

### 整改任务状态

```text
pending_acceptance
in_progress
pending_org_review
pending_security_review
completed
cancelled
```

必须建立统一迁移规则，尤其要明确：

- `resolved` 和 `fixed` 的区别；
- 工单取消后漏洞恢复为原状态还是统一回到 `pending`；
- 风险接受到期后恢复到 `confirmed` 还是其他状态；
- 工作版本废弃后，漏洞关联恢复是否影响已有工单；
- 误报、忽略、重复漏洞不得进入普通整改流程；
- `duplicate` 必须指向主漏洞；
- JSON 导入的合法原始状态必须保留语义，不能统一转换成 `pending`。

推荐语义：

```text
confirmed       已确认是真实漏洞，但尚未进入整改
in_progress     已进入明确整改过程
resolved        组织已完成处理，等待安全复核
fixed           集团安全复核确认已修复
risk_accepted   风险经审批接受，必须有期限和理由
false_positive  经安全判断确认是误报
ignored         明确不纳入当前治理，不代表不存在
```

JSON 导入状态对齐规则：

| JSON 原始值 | 标准值 | 页面中文 | 允许进入整改 |
|---|---|---|---|
| `pending` / `待处理` | `pending` | 待处理 | 否，等待判断 |
| `in_progress` / `处理中` | `in_progress` | 处理中 | 是，可进入整改 |
| `confirmed` / `已确认` | `confirmed` | 已确认 | 是 |
| `resolved` / `已处理` | `resolved` | 已处理 | 是，等待安全复核 |
| `fixed` / `已修复` | `fixed` | 已修复 | 否，已闭环 |
| `false_positive` / `误报` | `false_positive` | 误报 | 否 |
| `ignored` / `忽略` | `ignored` | 忽略 | 否 |
| `duplicate` / `重复` | `duplicate` | 重复 | 否，必须指向主漏洞 |
| `risk_accepted` / `风险接受` | `risk_accepted` | 风险接受 | 否，必须有期限和理由 |

导入时保留合法原始值和转换结果；未知值、非法严重等级、非法资产类型、非法时间和超长字段直接按行报错，不静默降级为 `pending`。页面和统计必须分别读取：漏洞状态、资产关联状态、整改状态，不能用一个状态字段代替三者。

## 6. 后续优先事项和实施顺序

不建议同时大面积重构权限、状态和页面。后续应按照“先堵越权、再打通主线、再完善治理”的顺序推进。

## 第一优先级：先堵住安全工单越权

### 目标

让旧工单和新整改任务的执行边界立即清晰，先消除现实中的越权风险。

### 工作项

1. 为旧组织工单增加明确的执行权限；
2. `Accept/Progress/Submit` 不再只依赖组织访问；
3. 子公司填报员默认不能执行组织级工单；
4. `individual` 工单服务端拒绝旧整改入口；
5. 收紧工单详情、漏洞明细和附件读取；
6. 禁止整改提交人进行最终安全复核；
7. 增加角色边界和接口级回归测试。

### 验收标准

- 子公司填报员调用旧工单 `accept/progress/submit` 返回 403；
- 子公司管理员只有在拥有组织整改权限时才可执行；
- individual 工单旧接口返回明确冲突错误；
- 未分配任务的组织用户不能读取个人整改材料；
- 外部厂商无法通过旧接口读取工单；
- 提交人不能完成最终安全复核；
- 既有合法整改流程不受影响。

这是当前最应该先做的工作，优先级高于页面优化和状态重构。

---

## 第二优先级：打通漏洞候选和资产候选协作主线

### 目标

让集团安全管理员能够从漏洞导入一直追踪到资产发布，但不获得正式资产写权限。

### 工作项

1. 增加资产候选协作查看权限；
2. 在漏洞待关联页面展示资产候选状态；
3. 在资产候选页面展示关联漏洞数量和最高严重性；
4. 展示责任组织、当前处理人和阻塞原因；
5. 增加催办、转交和请求组织确认；
6. 明确候选确认、工作版本生成、正式发布三个阶段。

### 验收标准

集团安全管理员能够回答：

```text
这个漏洞对应哪个候选资产？
候选属于哪个组织？
组织是否确认？
是否已经进入工作版本？
什么时候可以完成正式关联？
当前阻塞在哪一步？
```

但不能：

```text
直接修改组织正式资产
直接代替组织确认资产事实
```

---

## 第三优先级：修复资产草稿的所有权和并发问题

### 目标

避免组织内填报员互相覆盖草稿，建立可追责的资产填报过程。

### 工作项

1. 草稿增加 `version`；
2. 保存时增加 `expected_version`；
3. 版本冲突返回 409；
4. 增加 `created_by`、`assigned_to`、`last_edited_by`；
5. 普通填报员只能编辑本人或明确分配的草稿；
6. 管理员接管草稿必须记录原因；
7. 增加草稿变更历史和恢复能力。

### 验收标准

- 两人同时编辑时，后保存者不能静默覆盖；
- 普通填报员不能修改他人未授权草稿；
- 组织管理员可以接管，但审计中能看到接管人和原因；
- 提交快照能追溯到具体编辑人和版本。

---

## 第四优先级：收敛集团管理员的资产直写能力

### 目标

让资产入库遵循统一质量和审核流程，同时保留必要的紧急处置能力。

### 工作项

1. 默认集团管理员也使用工作版本；
2. 将直写正式资产改名为“紧急变更”；
3. 强制填写紧急原因；
4. 保存变更前后快照；
5. 核心资产需要二次审批；
6. 紧急变更后自动生成补录任务；
7. 增加紧急变更专项审计报表。

### 验收标准

常规资产入库不再出现：

```text
组织走完整流程，集团管理员无痕绕过流程
```

## 第五优先级：统一漏洞、工单、整改任务状态机

### 目标

让系统、页面、通知、统计和 JSON 导入使用同一套语义。

### 工作项

1. 建立状态迁移矩阵；
2. 明确每个状态的中文名称和业务语义；
3. 明确每个动作的前置状态和授权人；
4. 明确工单关闭对 finding 的影响；
5. 明确风险接受到期后的恢复规则；
6. 明确误报、重复、忽略的不可整改规则；
7. 为 JSON 导入增加原始状态、标准状态和转换原因；
8. 页面统一展示“漏洞状态、资产关联状态、整改状态”三个维度。

推荐页面不要只显示一个笼统的“状态”，而是分开展示：

```text
漏洞状态：已确认
资产状态：已进入工作版本
整改状态：待组织复核
```

## 第六优先级：外部厂商安全边界和全量越权测试

### 目标

确保外部厂商只能完成被授权的具体整改任务。

### 工作项

1. 补跨任务、跨漏洞、跨附件读取测试；
2. 补 grant 过期、撤销和厂商禁用测试；
3. 检查下载接口和事件接口；
4. 检查内部备注和安全证据脱敏；
5. 禁止外部厂商修改风险、误报和复核状态；
6. 对所有旧安全工单接口增加厂商拒绝测试。

## 9. 最终优先顺序

如果只能选择下一步最先做的事项，顺序如下：

```text
1. 收紧旧安全工单 Accept / Progress / Submit 权限
2. individual 工单彻底隔离旧整改接口
3. 收紧工单详情、漏洞明细和附件读取
4. 禁止整改提交人完成最终安全复核
```

其中前五项属于当前必须优先处理的 P0/P1 工作。页面优化、统计卡片和非关键流程体验，应排在这些权限和数据一致性问题之后。

## 9.1 建议的实施批次和退出条件

### 批次 A：安全边界止血（P0）

**范围**：旧安全工单权限、individual 入口、详情/附件读取、整改自我复核。

**必须先完成的接口级动作**：

- 新增并使用 `security_workorder.view/execute/assign/review/close`，不再用组织可见性代替工单动作权限；
- 子公司填报员不能执行旧组织工单；子公司管理员仅能在组织范围内执行；
- individual 工单的旧 `Accept/Progress/Submit` 返回明确的服务端错误；
- 未授权人员不能通过列表、通知、事件、漏洞明细或附件接口绕过详情边界；
- `submission.author_id == reviewer_id` 时，组织复核和安全复核均拒绝；
- 外部厂商不能访问旧组织工单接口。

**退出条件**：五类身份的正向/反向接口测试全部通过；既有合法的组织管理员整改和个人任务整改回归通过；没有只依赖前端隐藏按钮的权限控制。

### 批次 B：漏洞—资产协作主线（P0/P1）

**范围**：漏洞待关联、资产候选、组织确认、工作版本、正式资产关联。

**当前状态**：候选协作权限和集团安全管理员的全局只读/跟进范围已落地（迁移 `00066`、`00068`）；候选确认仍只属于集团管理员或符合组织策略的资产责任人。漏洞资产关联状态和整改状态已在 `00069` 持久化，但还未完成接口级验收和“漏洞待关联 → 资产候选 → 工作版本 → 正式资产”的全链路闭环。

2. 组织用户可从候选进入本组织工作版本，但不能跨组织读取或确认；

### 批次 C：草稿治理和资产数据可靠性（P1）

**范围**：草稿所有权、乐观锁、管理员接管、提交快照、恢复和审计。

**交付顺序**：

1. 资产草稿和业务系统草稿增加 `version`，保存携带 `expected_version`；
2. CAS 更新失败返回 409，前端明确提示“内容已被其他人更新”；
3. 填报员只编辑本人或明确分配的草稿；
4. 子公司管理员接管草稿时必须记录原因、接管人和时间；
5. 提交快照固定编辑人、版本和关键字段；
6. 保留草稿历史或可恢复记录，不允许直接物理覆盖而无法追责。

**退出条件**：并发保存不存在静默覆盖；跨用户编辑被拒绝；管理员接管和恢复可审计；草稿不会演变成另一套无审核正式台账。

### 批次 D：紧急变更与状态治理（P1/P2）

**范围**：集团管理员正式资产直写、漏洞/工单/任务状态、风险接受和 JSON 导入语义。

**交付顺序**：

1. 先定义状态迁移矩阵和禁止迁移，再修改页面文案；
2. 保留 JSON 原始状态、标准状态和转换原因；
3. `confirmed`、`in_progress`、`resolved`、`fixed`、`risk_accepted` 的语义和前置条件固定；
4. 工单取消、风险接受到期、工作版本废弃时恢复到可解释的原状态；
5. 集团管理员直写正式资产改成紧急变更，强制原因、前后快照和审计，并生成补录/复核任务；
6. 误报、忽略、重复漏洞不能进入普通整改，重复漏洞必须指向主漏洞。

**退出条件**：同一个漏洞在导入、页面、通知、工单和统计中的状态含义一致；任何状态变更都能回答“谁在什么依据下做了什么”。

### 批次 E：外部协作和持续验证（P2）

**范围**：厂商授权生命周期、脱敏和全量越权回归。

**退出条件**：grant 过期/撤销、厂商禁用、跨任务访问、跨附件下载和旧接口访问均有自动化测试；每次权限改动都能阻止回归。

| 旁路写路径 | 改造前 | 改造后 | 证据 |

### 本轮修复的两个真实业务缺陷

1. **恢复/编辑「变更申请」草稿必然冲突**：`ensureWorkingValueAvailable` 把正式台账行也当作唯一值占用，而变更申请草稿本身持有的正是该正式资产的 `(asset_type, normalized_value)`。因此任何一次「不改变值、只改名称」的编辑或恢复都会返回 `ErrConflict`。现已让该校验排除本行对应的正式资产 ID（`excludePublishedID`），保留对其他资产和其他草稿的唯一性保护。
2. **恢复创建草稿时责任人字段缺失**：资产与业务系统的恢复创建路径未写入 `version`/`assigned_to`/`last_edited_by`，新草稿在工作区里没有明确责任人；现已与普通创建路径对齐（`version=1`，责任人与最后编辑人为操作者）。

### 本轮暴露出的结构性结论

资产主线真正的风险不是“缺功能”，而是**同一份数据存在多条写路径，且只有部分路径受版本与审计保护**。目前已覆盖的只是直接工作区的创建/编辑/删除/废弃；仍然存在旁路：

| 旁路写路径 | 现状 | 需要的保护 |
|---|---|---|
| 任务内草稿的选择/取消选择、提交、退回 | 复用 `00067` 的 CAS，本轮已逐条确认递增版本并刷新最后编辑人 | 已完成 |
| 草稿恢复（`working_restore.go`） | 未纳入本轮 CAS 校验 | 恢复必须携带期望版本，且恢复本身是一次版本变更 |
| 资产候选接受生成工作版本 | 本轮已确认走 `CreateWorkingVersion` 事务，草稿初始 `version` 与审计一致 | 已完成 |

- 1、2、3 是**阻断型**：未验证的授权会继续扩散，漏洞丢失不可逆，闭环不通则资产与漏洞两张主线对不上账；
- 4、5、6 是**一致性型**：不改功能语义，只把“谁能改、改了什么、谁改的”记录完整，防止资产台账被静默覆盖；
- 7 是**体验与协作扩展型**：在权限和状态语义冻结前扩大入口，只会放大第 1～6 项的风险。

## 10. 结论

系统下一阶段不应继续单纯增加入口和按钮，而应优先完成以下三件事：

```text
第一，堵住旧安全工单的组织级越权。
第二，打通漏洞候选到资产候选再到工作版本的协作主线。
第三，把角色、对象和动作权限真正拆开。
```

最终职责边界应稳定为：

```text
集团管理员：管平台和制度
集团安全管理员：管漏洞和安全闭环
子公司管理员：管本组织资产和整改协调
子公司填报员：填数据、做被分配的整改
外部厂商：只做被授权的具体任务
```

只有在这条边界稳定后，资产、漏洞、安全工单和外部协作的后续功能扩展才不会继续叠加权限债务。

|---|---|---|---|
| 1 | 测试用 `'live'` / `'done'` 当作非法维度值，但 `live` 恰好是合法枚举值 | 测试缺陷（假阳性方向相反：断言“应失败”实际合法） | 改为 `'not-a-status'`；同时确认两个 CHECK 约束确实拒绝非法值 |
| 2 | 同一测试批次 + 同一资产 + 同一标题命中 `security_findings_batch_asset_title_unique` | 测试 fixture 缺陷：多个 finding 共用固定标题 | 标题改为 `状态维度测试漏洞-<finding_code>`，保持唯一索引的语义不变 |
| 3 | `sync_security_finding_remediation_status` 触发器回写 `security_findings` 时命中 `00052` 的 `guard_remediation_finding_write`，报 `finding is managed by a personal remediation task`（23514） | **真实设计缺陷**：两个迁移的完整性守卫互相冲突。只要存在有效整改任务，任何对 `security_findings` 的写入（包括系统派生的维度同步）都会被拒绝 | 三个同步函数（finding→关联维度、asset 软删除→关联维度、remediation_task→整改维度）在派生写入前用 `set_config('netassets.remediation_write','on',true)`，写完恢复原值。派生维护写入不被误判为“操作者绕过工单编辑漏洞”，而真正的操作者写入仍受 `00052` 拦截 |

第 3 项是本轮最重要的发现：**权限守卫的覆盖面必须按“写来源”区分，而不是按“目标表”粗粒度拦截**。旧守卫只看目标表，导致系统自己维护的派生状态也无法落库；修复方式是显式声明写入来源并在语句级恢复，而不是放宽守卫。

### 验收结果

| 命令 | 结果 |
|---|---|
| `migrate down && migrate up`（Podman） | 通过，版本回到 69 |
| `make test-backend` | **通过**，含 `internal/securityworkorder`（三维状态跟踪 + 非法值拒绝）与 `internal/remediation` |
| `make test-frontend` | **通过**，单测 + 生产构建 |

覆盖到的 `00069` 语义：

- 新建漏洞默认 `unlinked` + `not_started`；
- 绑定正式资产 → `live`；资产软删除 → `retired`；绑定工作版本草稿 → `pending`；
- 整改任务五态逐一同步到 `remediation_status`，任务 `cancelled` 回退 `not_started`；
- 整改维度**不得**改写 legacy `status`，也不得改写 `asset_link_status`；
- 两个维度的非法值被数据库 CHECK 直接拒绝。

### 验收后仍然不能标记完成的部分

`00069` 目前只是**持久化与同步**完成，以下属于 P1-3 未完成项：

- 导入 JSON 的**原始状态字段留存**；
- 原始值 → 标准值的**映射表**与转换原因；
- 状态**迁移矩阵**（哪些状态可流转到哪些状态、由谁操作）；
- `risk_accepted` 的**到期处理**；
- `duplicate` 的**主漏洞关系**；
- 统计、通知、前端页面统一改用对应维度，不再读 legacy `status` 的混合语义。

### 关于「编号字段」与「汇总卡片」的处理口径

这两项都是**已明确提出的需求**，本轮不实施，原因是：

- 隐藏编号属于纯展示层，但它会改变列表的默认列与导出列，需要与前端测试一起交付，塞进 P0 会拖慢权限闭环；
- 汇总卡片依赖三维状态的取数口径。在 `00069` 只完成持久化、`remediation_status` 与统计口径尚未统一之前，卡片上的“待处理”必然要在三套语义里选一个，等于把临时口径固化成产品口径。

结论：两项进入第三梯队第 9 位，但需求已冻结，不做二次决策。

### 明确不做的事

- 不用“隐藏前端按钮”充当权限交付；
- 不通过物理删除草稿来掩盖草稿管理问题；
- 不把无资产漏洞重新强制绑定测试批次；
- 不在三维状态语义冻结前扩展更多状态值；
- 不在卡片缺数字到明细/责任人的追溯时先做卡片。
